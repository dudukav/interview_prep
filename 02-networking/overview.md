# Сети и соединения: краткая справка

## Общая модель

Сетевой обмен удобно рассматривать слоями. Каждый слой решает свою задачу и использует нижележащий слой:

```text
Приложение       HTTP, WebSocket, DNS
Транспорт        TCP, UDP, QUIC
Сеть             IP
Канал            Ethernet, Wi-Fi
```

Приложение обычно работает не с Ethernet или IP напрямую, а с сокетом. Сокет связывает процесс с транспортным протоколом, локальным адресом и портом. Пара `IP:порт` указывает, на каком узле и каким процессом должен быть обработан трафик.

Пример пути HTTP-запроса:

1. Клиент получает IP-адрес домена через DNS.
2. Устанавливает TCP-соединение с сервером.
3. Для HTTPS выполняет TLS handshake.
4. Отправляет HTTP-запрос.
5. Сервер читает запрос, выполняет обработчик и возвращает ответ.
6. Соединение закрывается или переиспользуется.

Каждый этап может завершиться своей ошибкой. Поэтому `DNS error`, `connection refused`, `timeout`, ошибка сертификата и HTTP `500` — разные классы проблем.

## IP, адреса и порты

IP доставляет packets между сетевыми узлами. Он не гарантирует доставку, порядок или отсутствие дублей. Эти свойства при необходимости добавляет транспортный или прикладной протокол.

Порт — число от 0 до 65535, позволяющее операционной системе направить данные нужному процессу. Сервер обычно слушает известный порт, а клиент использует временный локальный порт. Один TCP connection определяется четырьмя значениями:

```text
source IP, source port, destination IP, destination port
```

Поэтому один серверный порт может обслуживать много клиентов одновременно.

IPv4-адрес делится маской/CIDR на network и host parts. Таблица маршрутизации выбирает наиболее специфичный route, затем next hop. `127.0.0.1`/`::1` — loopback: сервис, слушающий только localhost, недоступен с другой машины или Pod.

NAT изменяет адреса и/или порты на границе сети. Из-за source NAT сервер часто видит адрес proxy, node или gateway, а не исходного клиента. Доверять `X-Forwarded-For` можно только если заголовок очищает и устанавливает доверенный proxy; иначе клиент подделает его.

MTU ограничивает размер frame на участке пути. Слишком крупный IP packet фрагментируется или отбрасывается; Path MTU Discovery может ломаться при неверной фильтрации ICMP. На уровне приложения симптом выглядит как «маленькие запросы работают, большие зависают».

## DNS

DNS преобразует доменное имя в IP-адрес и возвращает другие записи домена. Результаты кэшируются на разных уровнях в пределах TTL. Изменение DNS не распространяется мгновенно, а один домен может возвращать несколько адресов для балансировки и отказоустойчивости.

Основные записи: `A`/`AAAA` — адрес, `CNAME` — alias, `MX` — почтовый маршрут, `TXT` — произвольные данные, `SRV` — service/port. Resolver может получить ответ из локального кэша или пройти цепочку recursive/authoritative servers.

`NXDOMAIN` означает, что имени нет; timeout — что resolver не получил ответ. Это разные проблемы. DNS discovery не гарантирует мгновенное переключение: клиенты и intermediaries кэшируют ответы, а уже открытые connections продолжают жить.

## TCP

TCP предоставляет приложению надёжный упорядоченный поток байтов:

- соединение устанавливается через handshake;
- байты нумеруются;
- потерянные сегменты передаются повторно;
- получатель подтверждает доставку;
- flow control защищает получателя;
- congestion control уменьшает нагрузку на сеть.

TCP не сохраняет границы сообщений. Если клиент сделал два `Write`, сервер может получить данные одним или несколькими `Read`. Приложению нужен framing: длина сообщения, разделитель или формат протокола.

TCP-подтверждение говорит о доставке данных TCP-стеку другой стороны, но не о завершении бизнес-операции. После неизвестного результата клиент не должен бездумно повторять неидемпотентный запрос.

При нормальном закрытии FIN завершает передачу в одном направлении, поэтому TCP поддерживает half-close. RST обрывает соединение немедленно. Состояние `TIME_WAIT` обычно остаётся у стороны активного закрытия, чтобы старые segments не попали в новое соединение и можно было повторить последний ACK. Большое число `TIME_WAIT` часто указывает на отсутствие connection reuse.

TCP keepalive обнаруживает давно мёртвого peer, но его системные интервалы обычно слишком велики для request deadline. Прикладной timeout и heartbeat решают другую задачу.

## UDP и QUIC

UDP передаёт отдельные datagrams без установления соединения. Потерю, повторы и изменение порядка должно учитывать приложение. UDP полезен, когда важна низкая задержка, допустима потеря части данных или поверх него строится собственный протокол.

QUIC работает поверх UDP, но сам реализует надёжность, шифрование и независимые streams. HTTP/3 использует QUIC, поэтому UDP в данном случае не означает отсутствие надёжной доставки на прикладном уровне.

## HTTP

HTTP работает по модели request-response. Запрос включает метод, target, headers и необязательное body. Ответ включает status code, headers и body.

Основные группы status codes:

- `2xx` — успешная обработка;
- `3xx` — перенаправление или работа с кэшем;
- `4xx` — запрос клиента нельзя выполнить в текущем виде;
- `5xx` — сервер не смог корректно обработать допустимый запрос.

Метод выражает намерение: `GET` читает, `POST` обычно создаёт или запускает команду, `PUT` заменяет представление ресурса, `PATCH` частично изменяет, `DELETE` удаляет. Безопасность и идемпотентность метода важны для кэширования и повторов.

HTTP/1.1 переиспользует соединения, HTTP/2 мультиплексирует streams внутри одного TCP connection, HTTP/3 переносит streams на QUIC. Версия транспорта не меняет базовую семантику методов и status codes.

## TLS и HTTPS

TLS обеспечивает:

- конфиденциальность — трафик шифруется;
- целостность — изменение данных обнаруживается;
- аутентификацию сервера — сертификат связывает домен с публичным ключом.

Клиент проверяет цепочку доверия, срок действия и соответствие имени в сертификате. TLS не заменяет аутентификацию пользователя, авторизацию и валидацию запросов.

Во время handshake клиент передаёт SNI, чтобы сервер выбрал сертификат для домена, и ALPN, чтобы согласовать HTTP/1.1 или HTTP/2. Ошибка TLS может быть вызвана неверным временем, просроченным сертификатом, отсутствующим intermediate certificate, несовпадением hostname или несовместимыми версиями/ciphers.

TLS завершается либо в приложении, либо на reverse proxy/load balancer. Если дальше трафик идёт без TLS, нужно явно определить доверенную сеть и способ передать исходную схему/адрес.

## Reverse proxy, load balancer и service discovery

Reverse proxy принимает запрос от имени backend: завершает TLS, маршрутизирует по host/path, ограничивает размер/скорость и добавляет observability. Load balancer распределяет соединения или запросы между экземплярами на L4 или L7.

Round-robin не учитывает длительность запросов; least-connections лучше отражает неравномерную работу, но тоже не знает реальную стоимость. Health checks должны удалять явно неготовый backend, а не перезапускать весь сервис из-за любой временной зависимости.

Sticky sessions привязывают клиента к экземпляру, упрощая локальное состояние, но ухудшают равномерность и failover. Предпочтительнее stateless handler и внешнее shared state, если это оправдано.

Service discovery сообщает доступные endpoints через DNS или registry. Он не решает retries, compatibility и graceful removal автоматически. При drain экземпляр сначала перестаёт получать новый трафик, затем заканчивает активные запросы.

## WebSocket

WebSocket создаёт долговременный двусторонний канал. После HTTP handshake обе стороны независимо отправляют frames. Серверу необходимо контролировать:

- heartbeat через ping/pong;
- дедлайны чтения и записи;
- медленных клиентов и размер очередей;
- ограничение размера сообщения;
- переподключение и повторную синхронизацию состояния;
- распределение соединений между экземплярами сервиса.

Если обновления редки и идут только от сервера к клиенту, polling, long polling или Server-Sent Events могут быть проще.

## Таймауты, повторы и пул соединений

У сетевой операции должны быть ограничены этапы ожидания: connect, TLS handshake, получение headers, чтение и запись. Общий deadline должен учитывать всю цепочку вызовов.

Retry допустим для временных ошибок и только в ограниченном числе. Нужны exponential backoff и jitter. Повтор может усилить перегрузку, а неидемпотентная операция — выполниться дважды.

Пул соединений уменьшает цену handshake, но требует лимитов и корректного возврата соединения. В Go для повторного использования HTTP connection важно дочитать и закрыть `response.Body`.

В `net/http` нельзя полагаться на client без ограничений времени. Общий `http.Client.Timeout` ограничивает весь обмен, а `Transport` позволяет отдельно задать dial, TLS handshake, response headers, idle pool и keep-alive. Для streaming общий timeout может быть неподходящим — нужны deadlines на активность и отмена context.

Слишком маленький pool создаёт очередь на клиенте, слишком большой способен перегрузить dependency. Важны метрики ожидания соединения, active/idle connections и ошибок reuse.

## Backpressure и длинные соединения

У WebSocket/TCP producer может генерировать данные быстрее, чем клиент читает. Нужна ограниченная per-client queue и политика: замедлить producer, отбросить промежуточные обновления, отключить медленного клиента или сохранить события в durable broker. Неограниченный buffer превращает медленное соединение в утечку памяти.

Heartbeat подтверждает живость прикладного пути, а reconnect должен использовать backoff+jitter. После reconnect клиенту часто нужна resynchronization по sequence/version, потому что часть событий могла быть пропущена.

## Типичные сетевые ошибки

| Симптом | Вероятный слой |
|---|---|
| `no such host`, `NXDOMAIN` | DNS/name |
| `connection refused` | IP достижим, но порт не слушается или firewall отверг |
| connect timeout | route, firewall drop, перегрузка или недоступный host |
| TLS handshake/certificate error | trust, hostname, срок, protocol |
| `connection reset by peer` | peer/proxy аварийно закрыл connection |
| `EOF`/`unexpected EOF` | поток завершился до ожидаемой границы сообщения |
| HTTP `502` | proxy не получил корректный ответ от upstream |
| HTTP `503` | сервис/endpoint временно не готов или перегружен |
| HTTP `504` | gateway не дождался upstream в свой timeout |

Точный смысл зависит от компонента, который вернул ошибку. Например, `504` от ingress не доказывает, что приложение само установило deadline.

## Минимальная диагностика

Диагностику ведут снизу вверх:

1. Разрешается ли доменное имя?
2. Доступен ли IP и открыт ли порт?
3. Устанавливаются ли TCP и TLS?
4. Какой HTTP-запрос реально отправлен?
5. Что отвечают proxy и приложение?
6. Есть ли тот же request/trace ID в логах?
7. Что показывают latency, errors и число соединений?

Полезные инструменты: `dig`, `curl -v`, `nc`, `lsof`, `ss`/`netstat`, Wireshark или `tcpdump`. Сначала используют наименее сложный инструмент, который способен подтвердить гипотезу.

Затем проверяют путь с обеих сторон: на каком адресе process слушает, доходит ли SYN, завершается ли TLS, какой proxy добавляет ответ и совпадают ли timestamps/trace ID. Packet capture используют для проверки конкретной гипотезы, а не как первый шаг.
