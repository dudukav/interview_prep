# Тестирование и диагностика Go

## Обычный тест

Файл заканчивается на `_test.go`, функция начинается с `Test`:

```go
func TestNormalizeEmail(t *testing.T) {
    got := NormalizeEmail(" A@EXAMPLE.COM ")
    want := "a@example.com"
    if got != want {
        t.Fatalf("NormalizeEmail() = %q, want %q", got, want)
    }
}
```

Тест проверяет публичное поведение и выдаёт сообщение, из которого видно got и want. `Fatal` прекращает текущий test goroutine; вызов `t.Fatal` из вспомогательной goroutine некорректен — error нужно передать основной.

## Table-driven tests

Одну операцию с разными входами удобно описать таблицей. `t.Run` создаёт subtests, которые можно выбирать через `-run`.

```go
tests := []struct {
    name string
    in   string
    want string
}{
    {"trim", " x@y.io ", "x@y.io"},
    {"lower", "X@Y.IO", "x@y.io"},
}
```

Если subtests запускаются параллельно, нужно внимательно относиться к shared state. В современном Go loop variables создаются на итерацию, но явные внешние переменные всё ещё можно захватить небезопасно.

## Test helpers и cleanup

Helper вызывает `t.Helper()`, чтобы ошибка указывала на строку caller. `t.Cleanup` регистрирует очистку, которая выполнится после теста и subtests. `t.TempDir` создаёт автоматически удаляемый каталог.

Тест не должен зависеть от текущего каталога, локального timezone, порядка map или уже запущенной БД без явной подготовки.

## Fakes, stubs и mocks

Для бизнес-логики часто достаточно небольшого fake, реализующего consumer-owned interface. Mock, проверяющий точный порядок каждого внутреннего вызова, делает тест хрупким.

Реальный SQL и ограничения проверяются integration-тестом. Fake map не способен доказать корректность SQL, транзакций и типов БД.

## HTTP-тесты

`httptest.NewRecorder` проверяет Handler без настоящего network listener. `httptest.NewServer` поднимает локальный server и полезен для проверки HTTP client, redirects и headers.

Нужно проверять status, content type, структуру body и важные side effects. Полное сравнение JSON-строки хрупко из-за whitespace и порядка полей; лучше декодировать ответ.

## Проверка context и конкурентности

Тест отмены должен иметь собственный короткий deadline, чтобы ошибка не повесила весь suite. Не следует полагаться только на `time.Sleep`; лучше ждать явный signal.

Для проверки утечки можно убедиться, что worker завершился через done channel. Глобальное число goroutines шумное, поэтому его используют осторожно.

Всегда полезно выполнять:

```text
go test ./...
go test -race ./...
go vet ./...
```

## Fuzzing

Fuzz test генерирует входы и сохраняет найденные случаи. Он полезен для parsers, encoders, validators и функций с инвариантами. Seed corpus должен содержать характерные граничные значения.

## Benchmarks

Benchmark принимает `*testing.B` и выполняет операцию `b.N` раз. Подготовку, которую не измеряют, выносят до timer или используют `b.StopTimer`. Для allocations применяют `-benchmem`.

Benchmark сравнивают в одинаковом окружении статистически, а не по одному запуску. Более быстрое число не оправдывает нечитаемую оптимизацию без реального bottleneck.

## Coverage

Coverage показывает выполненные statements, но не качество assertions и не полноту сценариев. Цель — уверенность в важном поведении, а не 100% любой ценой.

## pprof

Профили CPU показывают, где тратится процессорное время; heap — где выделяется или удерживается память; goroutine profile — где заблокированы goroutines; mutex/block profiles — contention.

Сначала воспроизводят нагрузку и формулируют проблему, затем снимают профиль. Оптимизация без профиля часто улучшает незначимый участок.
