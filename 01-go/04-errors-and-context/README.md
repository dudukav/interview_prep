# Ошибки, context и отмена

Собеседовательные нюансы: [error chains, Close, propagation context, Cause и каналы отмены](../interview-traps.md#4-errors-и-context).

## Ошибки как значения

Ожидаемая ошибка возвращается обычным значением:

```go
user, err := store.Get(ctx, id)
if err != nil {
    return User{}, fmt.Errorf("get user %d: %w", id, err)
}
```

Ошибка должна добавлять контекст, но сохранять исходную причину через `%w`, если caller должен её распознать. Текст ошибки обычно начинается со строчной буквы и не содержит лишнюю пунктуацию: несколько уровней wrapping сформируют одно сообщение.

Ошибку обрабатывают ровно там, где можно принять решение: повторить операцию, преобразовать её в API-ответ, выбрать fallback или завершить сценарий. Промежуточный слой обычно только добавляет контекст и возвращает ошибку выше.

## Классификация ошибок

Полезно отличать несколько независимых признаков:

- ожидаемая доменная ошибка: объект не найден, конфликт состояния, нарушено бизнес-правило;
- ошибка входа: неверный формат или значение;
- временная инфраструктурная ошибка: timeout, недоступная зависимость, исчерпание соединений;
- постоянная инфраструктурная ошибка: неверная конфигурация, несовместимая schema;
- отмена caller: `context.Canceled` не всегда означает поломку сервера;
- программная ошибка или нарушенный invariant: возможен panic и исправление кода.

Классификация определяет действие, а не только текст. Например, временная ошибка может допускать ограниченный retry, но только если операция идемпотентна и deadline не исчерпан.

## errors.Is и errors.As

Sentinel error обозначает известную категорию:

```go
var ErrNotFound = errors.New("not found")
```

`errors.Is(err, ErrNotFound)` проходит по error chain. `errors.As` находит ошибку определённого типа и извлекает её данные. Сравнивать wrapped error через `==` или анализировать текст ненадёжно.

Тип ошибки оправдан, если caller нужны поля:

```go
type ValidationError struct {
    Field string
    Err   error
}
```

Нельзя без необходимости экспортировать ошибки внутренней зависимости: это связывает внешний API с реализацией storage или transport.

Тип может поддержать собственный метод `Is`, если несколько конкретных значений относятся к одной категории. Делать это нужно осторожно: слишком широкое совпадение скрывает детали.

`errors.Join` объединяет несколько независимых ошибок в одну цепочку:

```go
return errors.Join(flushErr, closeErr)
```

`errors.Is` и `errors.As` обходят все ветви. `Join` полезен при cleanup нескольких ресурсов, но не заменяет продуманную семантику результата: caller должен понимать, могла ли основная операция уже выполниться.

## Ошибка на границе API

Внутренняя ошибка не должна напрямую становиться HTTP body: она может раскрыть SQL, адреса инфраструктуры или секреты. Transport layer сопоставляет стабильную категорию с публичным контрактом:

| Категория | Возможный HTTP-ответ |
|---|---|
| validation | `400` или `422` |
| unauthenticated | `401` |
| forbidden | `403` |
| not found | `404` |
| conflict | `409` |
| rate limited | `429` |
| временно недоступно | `503` |
| deadline сервера | `504` в роли gateway |
| неизвестная внутренняя ошибка | `500` |

Это не механическая таблица: статус зависит от роли сервиса и API-контракта. Клиенту возвращают безопасный `code`, понятное сообщение и request/trace ID; подробную cause chain сохраняют в telemetry.

## Логирование ошибок

Один и тот же error не стоит логировать на каждом слое. Иначе одна неудачная операция создаёт несколько одинаковых `ERROR` и искажает error rate. Обычно нижние слои возвращают контекст, а boundary, владеющий итогом операции, логирует один раз.

В структурированном логе полезны стабильное имя события, категория, operation, безопасные идентификаторы, latency и trace ID. Пароли, токены, полные персональные данные и тело произвольного запроса логировать нельзя.

`context.Canceled` из-за закрытия клиентом запроса часто является `INFO`/`DEBUG`, а не `ERROR`. `DeadlineExceeded` оценивают по тому, чей deadline истёк и пострадал ли SLO.

## Ошибки очистки ресурсов

`defer` гарантирует вызов cleanup, но не гарантирует обработку его ошибки. Для read-only ресурса ошибка `Close` часто вторична, а при записи `Flush`, `Commit` или `Close` может быть частью результата.

```go
func writeFile(path string, data []byte) (err error) {
    f, err := os.Create(path)
    if err != nil {
        return fmt.Errorf("create file: %w", err)
    }
    defer func() {
        err = errors.Join(err, f.Close())
    }()

    if _, err := f.Write(data); err != nil {
        return fmt.Errorf("write file: %w", err)
    }
    return nil
}
```

Для транзакции важно различать ошибку callback, `Commit` и `Rollback`. Успешный callback ещё не означает успешный commit.

## Panic

Panic подходит для нарушенного внутреннего инварианта или ошибки инициализации, после которой процесс не может продолжить работу. Неверные пользовательские данные, отсутствие строки и timeout — обычные errors.

HTTP middleware может recover, записать stack и вернуть `500`, сохранив работу процесса. После recover нельзя считать частично изменённое состояние автоматически корректным.

Recover действует только в той же goroutine, где произошёл panic. Если библиотека запускает goroutine, она должна сама определить политику panic. Нельзя использовать panic/recover как обычный механизм ветвления.

## Зачем нужен context.Context

Context переносит через границы API:

- сигнал отмены;
- deadline;
- request-scoped metadata.

Обычная сигнатура:

```go
func (s *Service) Get(ctx context.Context, id int64) (User, error)
```

`ctx` передают первым параметром, не хранят в struct как общее состояние и не заменяют им обязательные аргументы функции. Incoming request создаёт context, а все исходящие операции должны получить его или производный context.

## Дерево контекстов

`context.Background()` — корневой context приложения. `context.TODO()` временно обозначает место, где решение ещё не принято.

```go
ctx, cancel := context.WithTimeout(parent, 2*time.Second)
defer cancel()
```

Derived context отменяется, когда:

- вызван его `cancel`;
- отменён parent;
- истёк его deadline.

Отмена распространяется вниз, но не вверх. `cancel` нужно вызвать даже при наличии timeout: он освобождает timer и связи раньше.

## Done, Err и Cause

`ctx.Done()` возвращает channel, который закрывается при отмене. Закрытие удобно как broadcast: все receivers разблокируются.

```go
select {
case result := <-results:
    return result, nil
case <-ctx.Done():
    return Result{}, ctx.Err()
}
```

`ctx.Err()` возвращает `context.Canceled` или `context.DeadlineExceeded`. `WithCancelCause` и `context.Cause` позволяют отдельно сохранить смысловую причину отмены.

## Отмена должна быть кооперативной

Context сам не останавливает goroutine. Код должен ожидать `Done` в местах блокировки или периодически проверять `Err` в вычислительном цикле. Зависимость также должна поддерживать context: переданный, но игнорируемый `ctx` ничего не отменяет.

Неправильно:

```go
go slowWork() // не получает ctx и может утечь
```

Правильно:

```go
go func() {
    if err := slowWork(ctx); err != nil {
        // передать результат владельцу goroutine
    }
}()
```

## Context values

`WithValue` применяют для request-scoped метаданных, проходящих через API: trace ID или аутентифицированный principal. Его не используют для конфигурации, optional-параметров и зависимостей.

Key делают отдельного неэкспортируемого типа, чтобы packages не сталкивались именами. Доступ удобно закрыть type-safe функциями.

## Канал отмены без context

Внутри локального конкурентного алгоритма иногда достаточно `done <-chan struct{}`. Владелец создаёт channel и закрывает его ровно один раз:

```go
done := make(chan struct{})
defer close(done)
```

Workers слушают `<-done`. Закрытие — broadcast, отправка одного значения разбудит только одного receiver. Закрывать channel должен владелец сигнала, не каждый worker.

Для публичного или request-scoped API предпочтителен `context.Context`: он стандартно объединяет отмену, deadline и propagation.

## Проверка ошибок в тестах

Тест должен проверять контракт, а не полный текст цепочки:

```go
if !errors.Is(err, ErrNotFound) {
    t.Fatalf("expected ErrNotFound, got %v", err)
}

var validationErr *ValidationError
if !errors.As(err, &validationErr) {
    t.Fatalf("expected ValidationError, got %T", err)
}
```

Полное сообщение уместно проверять только когда оно является публичным контрактом. Для timeout/cancel тест использует управляемый context, а не `time.Sleep` с надеждой на планировщик.

## Частые ошибки

- создаётся `WithTimeout`, но `cancel` не вызывается;
- функция принимает `ctx`, но вызывает dependency с `context.Background()`;
- результат отправляется в channel после ухода consumer, и goroutine навсегда блокируется;
- context хранится в долгоживущем struct;
- `WithValue` используется как мешок параметров;
- отмена считается ошибкой уровня `ERROR`, хотя клиент штатно закрыл запрос;
- timeout каждого downstream-вызова длиннее оставшегося deadline родителя.
- ошибка сравнивается по строке или через `==` после wrapping;
- одна причина логируется на каждом слое;
- внутренняя ошибка БД или stack trace возвращается клиенту;
- игнорируется ошибка `Commit`, `Flush` или `Close` после записи;
- retry выполняется для любой ошибки без проверки идемпотентности.
