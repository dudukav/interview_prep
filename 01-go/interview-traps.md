# Go: частые ловушки на собеседованиях и тестах

Этот файл дополняет основную теорию. Здесь собраны места, где важно не просто помнить ответ, а правильно объяснить механизм.

Удобная схема ответа:

1. Назвать правило языка или библиотеки.
2. Применить его к конкретной строке.
3. Отделить гарантированное поведение от случайного порядка выполнения.
4. Предложить исправление и объяснить его компромиссы.

## 1. Основы языка

### `:=` может затенить переменную

```go
var err error

if enabled {
    value, err := load()
    _ = value
    _ = err
}

return err
```

Внутри блока объявлены новые `value` и `err`. Внешний `err` не изменился. Короткое объявление переиспользует имя только в том же lexical block и только если в левой части есть хотя бы одна новая переменная.

На собеседовании важно не говорить, что `:=` «всегда создаёт все переменные заново». Правило зависит от текущей области видимости.

### Нетипизированные константы и переполнение

```go
const x = 1 << 100
var y int = x // compile-time error
```

Нетипизированная константа может иметь очень большую точность, но при присваивании обязана быть представима целевым типом. Runtime-арифметика целых типов, напротив, выполняется в пределах конкретной разрядности.

Ловушки:

- `int` имеет платформенно зависимую ширину;
- деление двух integers отбрасывает дробную часть;
- unsigned arithmetic не подходит для маскировки отрицательных бизнес-значений;
- переполнение runtime integer не превращается автоматически в error.

### Аргументы `defer` вычисляются сразу

```go
x := 1
defer fmt.Println(x)
x = 2
```

Будет выведено `1`: аргумент вычислен при регистрации `defer`. Closure захватывает переменную и увидит значение на момент выполнения:

```go
defer func() { fmt.Println(x) }() // 2
```

Отложенные вызовы выполняются LIFO. Они запускаются при выходе из функции, включая return и panic, но не после `os.Exit` и не после фатального завершения runtime.

### `defer` может изменить named result

```go
func f() (n int) {
    defer func() { n++ }()
    return 1
}
```

`return 1` сначала присваивает `n = 1`, затем выполняется `defer`, поэтому результат равен `2`. Такой код допустим, но скрытое изменение результата ухудшает читаемость.

### `recover` имеет узкую область действия

`recover` останавливает panic только при прямом вызове из deferred function той же goroutine. Recover в соседней goroutine не перехватит panic. Вызов `recover` вне обработки panic возвращает `nil`.

### Closure захватывает переменную

Closure хранит доступ к переменной, а не обязательно копию значения. Но старую ловушку цикла нужно объяснять с учётом версии:

- с Go 1.22 переменные, объявленные самим циклом, создаются на каждую итерацию;
- при использовании заранее объявленной переменной с `=` одна переменная всё ещё переиспользуется;
- внешнее mutable state всё ещё можно небезопасно захватить.

```go
var v string
for _, v = range values {
    go func() { fmt.Println(v) }() // одна заранее объявленная v
}
```

### Порядок вычислений и порядок goroutines — не одно и то же

Порядок вычисления выражений определяется спецификацией не во всех мелких деталях. Порядок запуска и продолжения goroutines scheduler не гарантирует. `time.Sleep` не делает порядок корректным доказательством.

Если результат зависит от того, какая goroutine «успеет первой», нужны явные primitives синхронизации.

### Передача аргумента копирует значение

При вызове функции аргумент копируется. Для struct копируются поля; для slice, map, channel, function и interface копируется небольшой descriptor/header, который продолжает ссылаться на общее внутреннее состояние.

Поэтому утверждение «map передаётся по ссылке» неточно. Map — значение со ссылочной внутренней семантикой. Саму переменную map функция получает как копию, но изменения entries видны caller.

### Pointer не гарантирует heap

Compiler решает размещение через escape analysis. Локальное значение может оказаться в heap, а объект, созданный через `new`, — на stack. Семантически важно время жизни, а не место размещения.

### `init` и порядок инициализации

Dependencies инициализируются раньше импортирующего package. Затем вычисляются package variables по зависимостям и выполняются `init`. Порядок файлов package не стоит использовать как часть логики программы.

Большая работа, сеть или сложное состояние внутри `init` затрудняют тестирование и обработку ошибок.

## 2. Slices, maps, strings и память

### Slice — не массив

Slice содержит ссылку на backing array, длину и capacity. Копирование slice не копирует элементы.

```go
a := []int{1, 2, 3}
b := a[:2]
b[0] = 9
```

Изменение видно через `a`. Но после `append` результат зависит от capacity: если места хватает, запись попадёт в тот же array; иначе будет выделен новый.

### Результат `append` обязательно присваивать

```go
append(s, value) // compile-time error: результат не использован
s = append(s, value)
```

Даже когда append использует прежний backing array, длина хранится в новом slice descriptor. Другие slices не получают новую длину автоматически.

### Как ограничить влияние `append`

Полное slice expression ограничивает capacity:

```go
b := a[:2:2]
```

Следующий append вынужден выделить новый array. Это защищает оставшуюся часть `a` от перезаписи, но не отделяет уже доступные элементы `b[:2]`. Для полной независимости нужна копия.

### `copy` допускает пересечение

Built-in `copy` корректно работает с перекрывающимися slices и часто используется для удаления или сдвига элементов. После удаления pointer-like элементов хвост backing array может продолжать удерживать объекты. Его следует очищать, если массив долгоживущий.

### Nil slice и пустой slice

Оба имеют длину 0, оба можно append и range. Различия:

- только nil slice равен `nil`;
- JSON обычно кодирует nil slice как `null`, пустой — как `[]`;
- API-контракт иногда различает «не задано» и «задано пустым».

Нельзя сравнивать два slices через `==`; доступны только сравнение с `nil` или специальные функции сравнения.

### Nil map читается, но не принимает записи

```go
var m map[string]int
fmt.Println(m["x"]) // 0
m["x"] = 1          // panic
```

`delete` из nil map безопасен. `len` равен 0. Перед записью нужна инициализация через `make` или literal.

### Значение из map не addressable

```go
type Counter struct{ N int }
m := map[string]Counter{"x": {}}
m["x"].N++ // compile-time error
```

Map может перемещать entries при росте, поэтому получить устойчивый pointer на element нельзя. Нужно прочитать копию, изменить и записать обратно либо хранить pointers:

```go
v := m["x"]
v.N++
m["x"] = v
```

### Отсутствующий ключ неотличим от zero value без `ok`

```go
v, ok := m[key]
```

Один `v := m[key]` не позволяет понять, был ли ключ. Это особенно важно для `bool`, чисел и pointers.

### Порядок map не определён

Нельзя писать тест, ожидающий определённый порядок `range map`. Для стабильного результата ключи собирают и сортируют.

Изменение map во время iteration имеет специальные, но неудобные правила: удалённый ещё не встреченный key не будет выдан, новый key может быть выдан или пропущен. Такой код лучше не строить на случайном результате.

### Concurrent map access

Обычная map не поддерживает конкурентную запись и одновременные read/write без синхронизации. Даже если программа «работает локально», это data race и может привести к runtime failure.

Исправления: Mutex, владение state одной goroutine или `sync.Map` для подходящего специализированного сценария. `sync.Map` не является универсально более быстрой map.

### String — bytes, а `range` — runes

`len(s)` возвращает bytes. `s[i]` — byte. `range` возвращает byte offset и Unicode code point (`rune`). Один визуальный grapheme может состоять из нескольких runes.

Нельзя безопасно обрезать пользовательский текст произвольным byte index. Но для ASCII protocol tokens работа с bytes может быть правильным выбором.

### Преобразования string и `[]byte`

Обычные преобразования создают независимые данные, хотя compiler способен оптимизировать некоторые внутренние случаи без изменения семантики. Не следует строить корректность на предположении о zero-copy.

### JSON и экспортируемые поля

`encoding/json` видит экспортируемые поля. Частые ловушки:

- `omitempty` скрывает zero value, а не только «не передано»;
- `time.Time` — struct, и ожидания от `omitempty` часто неверны;
- числа при декодировании в `any` становятся `float64`, если не использовать `UseNumber`;
- неизвестные поля по умолчанию игнорируются;
- nil и empty collections могут иметь разный JSON.

Для внешнего API лучше отдельный DTO, а не прямая сериализация domain struct.

### GC освобождает память, но не ресурсы

Garbage collector не гарантирует своевременное закрытие files, sockets, response bodies и database rows. Ресурс закрывают явно.

Память может оставаться достижимой через маленький subslice, cache, goroutine stack или timer. «GC есть» не означает «утечек быть не может».

## 3. Методы, интерфейсы и generics

### Method set `T` и `*T`

У `T` есть методы с receiver `T`. У `*T` — методы с receiver `T` и `*T`. Если интерфейс требует pointer-receiver method, значение `T` его не реализует.

Compiler может автоматически взять адрес в обычном вызове:

```go
v.Mutate() // может стать (&v).Mutate(), если v addressable
```

Но это не добавляет метод в method set `T` при проверке интерфейса.

### Не каждое значение addressable

Map element и результат функции не всегда позволяют автоматическое взятие адреса для pointer method:

```go
m[key].Mutate() // нельзя, если Mutate имеет pointer receiver
makeValue().Mutate()
```

Нужно сохранить значение в переменную или изменить модель хранения.

### Typed nil внутри interface

Interface равен `nil`, только когда отсутствуют и dynamic type, и dynamic value.

```go
var p *MyError
var err error = p
fmt.Println(err == nil) // false
```

Функция, возвращающая `error`, должна явно вернуть `nil` при отсутствии ошибки, а не typed nil pointer.

### Сравнение interface может вызвать panic

Два interface values можно синтаксически сравнить, но если их одинаковый dynamic type несравним — например, slice или map — сравнение вызывает panic.

```go
var a any = []int{1}
var b any = []int{1}
fmt.Println(a == b) // panic
```

### Pointer на interface обычно не нужен

Сам interface уже содержит dynamic value. Функция принимает interface по значению. `*interface` редко является правильным способом получить полиморфизм и обычно усложняет API.

### Interface лучше объявлять у consumer

Если service нужен только `Get`, интерфейс из четырёх CRUD-методов заставляет fake реализовать лишнее и связывает consumer с producer. Маленький consumer-owned interface проще тестировать и изменять.

Но интерфейс не обязателен заранее. Если polymorphism и test seam не нужны, concrete type проще.

### Embedding — продвижение, не наследование

Outer type не становится subtype embedded type. Методы могут продвигаться, но конфликт имён требует явного выбора. Публичное embedding может случайно расширить API внешнего типа.

### Nil receiver допустим, но не магический

Метод pointer receiver можно вызвать на nil pointer, пока сам метод не разыменует receiver. Это иногда полезно для структур данных, но неожиданная поддержка nil усложняет контракт. Нужно решать явно.

### Type assertion может panic

Форма `v := x.(T)` panic при несовпадении. Для внешних данных или необязательного capability используют `v, ok := x.(T)`. Type switch полезен для нескольких вариантов.

### Generics и interfaces отвечают на разные вопросы

Interface value хранит runtime dynamic type и выражает поведение. Type parameter создаёт compile-time семейство реализаций для набора типов.

Ловушки:

- constraint может использоваться не так, как обычный runtime interface;
- `comparable` разрешает `==`, но не задаёт ordering;
- `any` не означает, что доступны любые операции;
- type inference не обязана угадывать параметр, который не связан с аргументами;
- generic abstraction ради одного простого случая может ухудшить API.

Начиная с Go 1.27 методы могут объявлять собственные type parameters. На собеседовании важно сначала уточнить версию Go: старый ответ «generic methods запрещены» больше не универсален.

## 4. Errors и context

### Ошибку добавляют к контексту, а не логируют на каждом слое

```go
return fmt.Errorf("load user %d: %w", id, err)
```

`%w` сохраняет цепочку для `errors.Is/As`. `%v` превращает причину только в текст. Логировать одну ошибку на каждом уровне обычно создаёт дубли; чаще её оборачивают, а логируют на границе операции.

### Текст ошибки — плохой API

Нельзя определять семантику через `strings.Contains(err.Error(), ...)`. Используют sentinel error, конкретный error type или собственный `Is`.

При этом exported sentinel/type становится частью контракта. Не следует бездумно раскрывать ошибки внутреннего driver.

### `errors.Is`, `errors.As` и `errors.Join`

- `Is` проверяет семантическое соответствие по chain/tree;
- `As` извлекает подходящий тип;
- `Join` объединяет несколько причин.

`errors.As` получает pointer на целевую переменную. Для pointer error type это часто выглядит как `var target *MyError; errors.As(err, &target)`.

### Ошибка `Close` может быть важна

Для read-only resource часто достаточно `defer Close`, но при записи ошибка flush/close может означать потерю данных. Named result или явный close позволяют не потерять её, сохранив первичную ошибку операции.

### Context не останавливает код принудительно

Отмена закрывает `Done`. Функция должна сама наблюдать сигнал или вызвать API, умеющее работать с context. CPU loop без проверки и blocking call без context продолжатся.

### Context распространяют, а не заменяют

Функция, получившая `ctx`, не должна вызывать dependency с `context.Background()`: так теряются отмена, deadline и metadata.

Derived deadline не должен превышать deadline parent. Фактически child всё равно отменится раньше вместе с parent.

### `cancel` вызывают всегда

После `WithCancel`, `WithTimeout` или `WithDeadline` вызывают возвращённую функцию на всех путях, обычно через `defer cancel()`. Это освобождает timer и ссылки parent раньше.

### `Done` может быть nil

У context без отмены `Done()` может вернуть nil channel. Receive из него блокируется навсегда, что нормально внутри `select`: соответствующий case просто никогда не готов.

### `Err` и `Cause` — не одно и то же

`Err` возвращает стандартную категорию `Canceled` или `DeadlineExceeded`. `Cause` может вернуть более содержательную причину, заданную через cause-aware constructor.

### `WithValue` — не контейнер зависимостей

Допустимы request-scoped данные, проходящие через границы API: trace ID, principal. Конфигурация, logger, database и optional business arguments должны передаваться обычными зависимостями и параметрами.

Key не должен быть обычной строкой общего назначения: package создаёт собственный неэкспортируемый тип и type-safe accessors.

### `WithoutCancel` требует осторожности

Отделение от отмены parent иногда нужно для короткой фоновой финализации, но легко создаёт работу без lifetime owner. Такая операция всё равно должна иметь собственный deadline и понятного владельца.

### Отмена через channel

Закрытие `chan struct{}` — broadcast. Отправка одного `struct{}{}` разбудит только одного receiver. Канал отмены закрывает владелец сигнала; несколько workers не должны независимо пытаться его закрыть.

## 5. Goroutines, channels и shared state

### Четыре состояния channel

| Операция | nil channel | открытый channel | закрытый channel |
|---|---|---|---|
| receive | блокируется навсегда | ждёт/получает значение | сразу даёт buffered value, затем zero value и `ok=false` |
| send | блокируется навсегда | ждёт/отправляет | panic |
| close | panic | закрывает | panic |

Эта таблица объясняет большую часть тестовых задач на channels.

### Закрытие — не «удаление канала»

Channel закрывают, чтобы сообщить receivers, что новых значений не будет. Его не нужно закрывать для GC. Обычно закрывает sender или coordinator, знающий, что всех senders больше нет.

Receiver не закрывает input только потому, что закончил читать.

### Receive без `ok` из закрытого channel всегда готов

В `select` closed channel выбирается снова и снова. Если после закрытия case больше не нужен, переменной channel присваивают `nil` или выходят из цикла.

### Буфер меняет блокировку, но не исправляет ownership

Buffer способен отложить deadlock или позволить одной goroutine завершить send после ухода receiver. Но он не отвечает на вопросы:

- кто закрывает channel;
- сколько сообщений максимум в памяти;
- что делать при отмене;
- как сообщить об ошибке.

Размер буфера должен следовать из модели backpressure, а не подбираться случайно.

### `select` не задаёт приоритет

Если готовы несколько cases, выбирается один из них. Нельзя считать, что `ctx.Done()` обязательно победит готовый send или receive. Если нужен строгий приоритет отмены, структуру алгоритма проектируют отдельно и всё равно учитывают race между событиями.

### `default` легко создаёт busy loop

Цикл `select { default: }` без blocking operation постоянно занимает CPU. Неблокирующие операции нужны редко; чаще следует ждать channel, timer или context.

### Send тоже должен уметь отменяться

Даже если worker проверил context перед вычислением, он может навсегда застрять на отправке результата после ухода consumer:

```go
select {
case out <- result:
case <-ctx.Done():
    return
}
```

### Для каждой goroutine нужен lifetime owner

Нужно ответить:

- кто её запустил;
- какое событие завершает её;
- кто ждёт завершения;
- куда уходит ошибка;
- может ли блокирующая операция быть отменена.

Если ответа нет, высок риск goroutine leak.

### `WaitGroup.Add` выполняют до запуска

Если `Add` находится внутри goroutine, `Wait` может увидеть нулевой счётчик и завершиться раньше. `Done` ставят через defer в начале worker.

Нельзя копировать WaitGroup после начала использования. Нельзя повторно использовать новый цикл `Add` одновременно с ещё выполняющимся `Wait` без соблюдения его контракта.

### Mutex защищает инвариант, а не строку кода

Все обращения к связанному state должны соблюдать один locking protocol. Возврат pointer/slice/map на внутреннее mutable state может незаметно вывести данные из-под защиты.

Структуру с Mutex нельзя копировать после использования. Pointer receiver помогает избежать случайной копии lock.

### RWMutex не автоматически быстрее

Он имеет более сложную координацию и полезен при измеренном сценарии: много достаточно долгих чтений и мало записей. Для коротких critical sections обычный Mutex часто проще и быстрее.

Ни Mutex, ни RWMutex не являются reentrant: повторный Lock той же goroutine ведёт к deadlock.

### Atomic подходит не для каждого инварианта

Atomic counter прост. Согласованное изменение нескольких полей — уже составной инвариант, для которого Mutex часто яснее. Смешивать atomic и обычный доступ к одной памяти нельзя.

### `sync.Once` запоминает даже panic

Если функция, переданная `Once.Do`, panic, Once считается выполненным. Он не предоставляет retry. Инициализация с error/retry требует другой конструкции.

### Race и логическая гонка различаются

Data race — несинхронизированный конфликт памяти, который ищет race detector. Логическая race возможна даже при отсутствии data race:

```text
прочитать баланс → проверить → отдельным запросом списать
```

Каждый доступ может быть защищён, но последовательность не атомарна.

### Race detector не доказывает отсутствие гонок

Он обнаруживает только paths, реально выполненные под инструментированной сборкой. Нужно запускать релевантную нагрузку и тесты. Чистый отчёт — полезный сигнал, но не формальное доказательство.

### Timer и Ticker имеют lifetime

Ticker останавливают, когда он больше не нужен. `time.After` удобно для единичного ожидания, но создание его на каждой итерации горячего цикла создаёт timers и лишнюю работу. Для управляемого повторного ожидания используют `Timer` и аккуратно работают с `Stop/Reset` согласно API текущей версии Go.

## 6. Стандартная библиотека и I/O

### `io.Reader` может вернуть `n > 0` и error одновременно

Сначала обрабатывают прочитанные bytes, затем error. Нельзя выбрасывать `n` только потому, что `err == io.EOF`. Один `Read` также не обязан заполнить buffer.

Для точного объёма есть `io.ReadFull`; для потока — `io.Copy`; для внешнего неограниченного input — `io.LimitReader` или специализированный лимит.

### `defer` в большом цикле копит ресурсы

`defer` выполняется при выходе из окружающей функции, не в конце iteration. Открытие файла внутри большого цикла с `defer f.Close()` может исчерпать descriptors. Итерацию выносят в отдельную функцию или закрывают явно.

### `bufio.Writer` требует Flush

Успешная запись в buffer ещё не означает запись в нижележащий Writer. Ошибку `Flush` нужно проверять. Аналогично финальная ошибка может проявиться при `Close` encoder/compressor/file.

### `bufio.Scanner` имеет лимит token

После цикла обязательно проверяют `scanner.Err()`. Для длинных строк увеличивают buffer до сканирования или выбирают `bufio.Reader`.

### HTTP transport error и HTTP status — разные вещи

`client.Do` возвращает nil error для корректно полученного `500`. Transport error означает, что нормальный HTTP response не был получен: DNS, connect, TLS, cancellation и подобное.

Приложение отдельно проверяет `resp.StatusCode`.

### `resp.Body` закрывают

Если `Do` вернул response, body закрывают. Для повторного использования HTTP/1 connection body обычно нужно дочитать до конца в разумных пределах. Нельзя безлимитно `ReadAll` внешнего ответа ради reuse.

### `http.Client` переиспользуют

Внутри Transport находится connection pool. Создание нового client/transport на каждый запрос теряет pooling и способно накопить sockets. Client безопасен для concurrent use.

Нужны request context и разумные timeouts. Один общий client timeout ограничивает весь exchange, а Transport имеет отдельные настройки этапов.

### Request context прекращается вместе с клиентом

Handler должен передавать `r.Context()` вниз. Замена на `Background()` отрывает БД или downstream call от отмены запроса.

Но context cancellation не означает, что уже совершённый внешний side effect откатился.

### Headers отправляются один раз

Первый `WriteHeader` фиксирует status. Первый `Write` без него неявно отправляет `200`. Изменение headers после этого может не попасть клиенту.

Поэтому желательно подготовить результат или error до начала записи response, если protocol не streaming.

### HTTP body нужно ограничивать

Клиент контролирует размер входа. `json.Decoder` сам по себе не устанавливает безопасный предел. Server применяет лимит, валидирует content type и при строгом контракте проверяет неизвестные поля и лишний JSON после первого value.

### `time.Duration` — наносекунды

```go
timeout := 5 // int, не пять секунд
```

При преобразовании `time.Duration(timeout)` получится 5 наносекунд. Единицу нужно умножить явно или парсить из конфигурации через `time.ParseDuration`.

### `time.Time` содержит больше, чем видно

Сравнение через `==` учитывает внутренние данные, включая location/monotonic representation. Для момента времени обычно используют `Equal`. После сериализации монотонная часть теряется.

### Environment отсутствует и пуст — не всегда одно и то же

`os.Getenv` возвращает пустую строку в обоих случаях. `os.LookupEnv` позволяет различить отсутствие переменной и явно пустое значение.

### Package-level mutable state усложняет тесты

Глобальный client, cache или config создаёт неявные зависимости и конфликты параллельных тестов. Неизменяемые constants и stateless helpers нормальны; mutable dependencies лучше собирать явно в `main`.

### Import cycle — сигнал направления зависимостей

Go запрещает import cycles. Исправление — не объединять всё в один package автоматически, а определить ownership, вынести общий контракт к consumer или перевернуть зависимость через interface.

## 7. Тестирование и диагностика

### Тестируется поведение, а не реализация

Хрупкий mock проверяет точный порядок внутренних вызовов и ломается при безопасном refactoring. Лучше проверять результат и важные side effects. Interaction assertion нужна, когда сам вызов является контрактом.

### `t.Fatal` вызывают из test goroutine

`FailNow`, а значит `Fatal/Fatalf`, завершает goroutine, которая его вызвала. Вызов из worker goroutine не останавливает основной тест корректным образом. Worker передаёт error через channel, а assertion делает test goroutine.

### `t.Parallel` меняет время выполнения

Parallel subtest приостанавливается и продолжится вместе с другими parallel tests. Нельзя разделять mutable global state, один database row, environment variable или working directory без изоляции.

`t.Setenv` и `t.Chdir` имеют ограничения при parallel execution, потому что меняют process-wide state.

### Сравнение map/slice через `==` невозможно

Используют `slices.Equal`, `maps.Equal`, специализированное сравнение или `reflect.DeepEqual` с пониманием его семантики. Nil и empty могут считаться по-разному в зависимости от инструмента и нужного контракта.

### Тесты не должны ждать «примерно достаточно»

```go
time.Sleep(10 * time.Millisecond)
```

На медленном CI этого может не хватить, а локально тест зря тормозит. Лучше explicit completion signal или polling с deadline и небольшим интервалом.

Любой тест concurrent code должен иметь верхнюю границу ожидания, чтобы ошибка не повесила suite.

### Cleanup регистрируют сразу

После успешного создания ресурса сразу вызывают `t.Cleanup`. Так cleanup выполнится и при последующем `Fatal`. Helper отмечают через `t.Helper`, чтобы failure указывал на caller.

### Table-driven test — не цель сама по себе

Таблица полезна, когда cases выполняют одну и ту же проверку. Если каждый case требует разных сложных ветвей, обычные отдельные tests читаются лучше.

Названия subtests должны объяснять поведение, а не быть просто `case_1`.

### Fake не проверяет реальную интеграцию

In-memory fake repository не воспроизводит SQL types, constraints, isolation и driver behavior. Бизнес-логику проверяют fake, а boundary — integration test с настоящей технологией.

### Coverage не измеряет качество assertions

100% statement coverage может ничего не проверить. Важнее branches бизнес-правил, error paths, границы и свойства результата. Coverage используют как карту непройденного кода, а не единственную цель.

### Benchmark легко измеряет не то

Setup исключают из измерения, результат не дают compiler полностью устранить, allocations смотрят через `-benchmem`. Сравнивают несколько запусков статистически в одинаковом окружении.

### Fuzz test проверяет invariant

Полезные свойства:

- encode/decode round trip;
- parser никогда не panic;
- normalizer идемпотентен;
- результат удовлетворяет ограничениям.

Fuzzing не заменяет осмысленные example cases, а дополняет их.

### `-race` и обычный test — разные проверки

Race build медленнее и меняет timing. Следует запускать и обычные tests, и race detector. Ошибка, исчезающая под `-race`, всё равно может быть реальной timing-dependent проблемой.

### Pprof показывает симптом разных типов

- CPU profile — где тратится процессор;
- allocs — где создаются allocations;
- heap — что остаётся живым;
- goroutine — где goroutines ждут;
- block/mutex — где contention.

Heap growth не всегда утечка, а большое число goroutines не всегда проблема. Сначала формулируют ожидаемое состояние и воспроизводят нагрузку.

## Быстрый чек-лист перед собеседованием

Нужно уметь без запуска кода объяснить:

- что копируется при передаче slice, map, struct и interface;
- когда append меняет общий backing array;
- разницу nil и empty slice, nil и closed channel;
- method sets `T` и `*T`;
- typed nil внутри interface;
- вычисление `defer` и named results;
- wrapping errors и `errors.Is/As`;
- распространение и кооперативную природу context cancellation;
- ownership закрытия channels;
- data race, logical race и goroutine leak;
- обязательные действия вокруг HTTP response body;
- различие unit, integration и race checks;
- почему конкретный ответ зависит или не зависит от scheduler.
