# Качество и наблюдаемость: краткая справка

## Качество — это не только тесты

Качество backend-сервиса включает корректность бизнес-логики, понятные контракты, устойчивость к сбоям, безопасность, производительность и возможность диагностировать проблему. Автоматические тесты уменьшают риск изменений, но не доказывают отсутствие всех ошибок.

Полезная стратегия сочетает:

- проверки кода до merge;
- тесты разных уровней;
- контролируемый deploy;
- логи, метрики и traces;
- цели надёжности;
- анализ инцидентов и улучшение системы.

## Уровни тестирования

### Unit

Проверяет небольшую единицу логики быстро и детерминированно. Внешние зависимости заменяют небольшими fakes или stubs только там, где это помогает проверить поведение. Unit-тест не должен повторять реализацию построчно.

### Integration

Проверяет взаимодействие с реальной технологией: SQL, миграциями, Kafka protocol или HTTP adapter. Такие тесты находят ошибки, которые mock скрывает: несовместимый тип, неправильный запрос, транзакцию или сериализацию.

### Contract

Проверяет, что клиент и сервер одинаково понимают API или событие. Это особенно важно, когда части системы выпускаются независимо.

### E2E

Проверяет критический сценарий через развёрнутую систему. Он даёт высокую уверенность в интеграции, но медленный и сложный для диагностики. E2E-набор должен быть небольшим и устойчивым.

## Хороший тест

Хороший тест:

- проверяет наблюдаемое поведение;
- имеет понятные входные данные и ожидаемый результат;
- не зависит от порядка других тестов;
- контролирует время и случайность;
- выдаёт понятную причину падения;
- очищает созданное состояние;
- не требует ручной подготовки.

Flaky test нельзя просто перезапускать до успеха: он разрушает доверие к pipeline. Нужно найти источник недетерминизма — общее состояние, гонку, время, сеть или нестабильное ожидание.

## Нагрузочное тестирование

Сценарий нагрузки должен быть похож на реальное использование: соотношение endpoints, размер данных, прогрев, скорость роста и продолжительность. Основные виды:

- load — ожидаемая рабочая нагрузка;
- stress — поиск предела и поведения за ним;
- spike — резкий скачок;
- soak — длительная проверка утечек и деградации.

Собирают throughput, errors, latency percentiles, CPU, память, GC, pool БД, блокировки и очереди. Результат без профиля нагрузки и критериев успеха нельзя корректно интерпретировать.

## Observability

Monitoring показывает заранее выбранные признаки, observability помогает исследовать внутреннее состояние по внешним сигналам, включая неизвестные заранее вопросы.

Три основных сигнала:

- **logs** — отдельные события и контекст;
- **metrics** — агрегированные числовые ряды;
- **traces** — путь запроса через распределённые компоненты.

Их связывают trace/request ID. При этом high-cardinality значения подходят для logs и traces, но опасны как labels метрик.

## Логи

Структурированный лог содержит стабильное название события и поля, а не только строку. Уровни используют осмысленно:

- debug — подробности диагностики;
- info — нормальные значимые события;
- warn — необычное состояние, с которым сервис справился;
- error — операция не выполнена и требует внимания.

Логи не должны содержать пароли, access tokens, полные платёжные данные и ненужные персональные сведения. Ошибку логируют там, где известен итог операции и достаточно контекста.

## Метрики

Для HTTP-сервиса используют RED:

- Rate — скорость запросов;
- Errors — число или доля ошибок;
- Duration — распределение latency.

Для ресурсов используют USE:

- Utilization — доля занятости;
- Saturation — очередь или отложенная работа;
- Errors — ошибки ресурса.

Counter только растёт, gauge увеличивается и уменьшается, histogram распределяет наблюдения по buckets. Для latency важны p95/p99, потому что среднее скрывает медленный хвост.

Labels должны иметь ограниченное число значений. `method` и шаблон route допустимы; `user_id`, полный URL и request ID создают cardinality explosion.

## Tracing

Trace состоит из spans. Span описывает одну операцию, её длительность, статус и связь с родителем. Контекст trace передаётся через HTTP headers и metadata сообщений.

Tracing полезен для поиска медленного звена и понимания каскадных вызовов. Sampling ограничивает объём данных. Trace не заменяет метрики: он показывает отдельные примеры, а не полную статистику системы.

## SLI, SLO и error budget

SLI измеряет пользовательское качество. SLO задаёт цель на период. Например:

```text
99.9% корректных HTTP-ответов за 30 дней
```

Оставшаяся допустимая доля ошибок образует error budget. Быстрое расходование budget — сигнал замедлить рискованные изменения и улучшить надёжность. Alert лучше строить по угрозе SLO, а не по каждому краткому скачку технической метрики.

## Dashboards и alerts

Dashboard сервиса должен быстро отвечать:

1. Получает ли сервис нормальный объём трафика?
2. Видят ли пользователи ошибки или высокую latency?
3. Насыщены ли CPU, память, goroutines, pool или очереди?
4. Какая зависимость деградировала?
5. Связано ли изменение с новой версией?

Alert должен быть actionable: иметь владельца, серьёзность, понятное условие и runbook. Если при alert ничего не нужно делать, это, вероятно, dashboard-сигнал, а не оповещение.

## Production readiness

Перед выпуском проверяют:

- health и readiness endpoints;
- timeouts и graceful shutdown;
- миграции и обратную совместимость;
- лимиты ресурсов и pools;
- dashboards и alerts;
- обработку retry и перегрузки;
- backup/restore для данных;
- rollout и rollback;
- отсутствие секретов и персональных данных в telemetry.

После инцидента важно не искать виновного, а восстановить timeline, определить технические и процессные причины и назначить конкретные улучшения с владельцами.
