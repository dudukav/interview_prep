# Инструменты разработки: краткая справка

## Общий рабочий цикл

Типичный путь изменения backend-сервиса:

```text
локальная ветка → commit → review → CI → container image → registry → deploy → monitoring
```

Git хранит историю исходного кода. Bash и другие shell-инструменты автоматизируют локальные операции и pipeline. Docker упаковывает приложение с runtime-окружением. CI проверяет изменение, CD доставляет его в окружение.

## Git: модель данных

Git хранит snapshots проекта и связи между commits. Commit содержит ссылку на дерево файлов, автора, сообщение и родительский commit. Branch — подвижная ссылка на commit, `HEAD` указывает на текущую позицию.

Рабочая копия проходит три состояния:

```text
working tree → staging area/index → commit
```

Это позволяет включить в commit только логически связанные изменения. Хороший commit собирается, проходит тесты и объясняет одно намерение.

### Merge и rebase

Merge создаёт commit, объединяющий две линии истории. Rebase переносит commits на новую основу и переписывает их идентификаторы. Rebase удобен для очистки локальной истории, но опубликованную общую историю нельзя переписывать без согласования.

Конфликт означает, что Git не способен автоматически совместить изменения. Разработчик должен понять итоговое желаемое состояние, отредактировать файл, проверить результат и только затем продолжить операцию.

### Отмена изменений

Способ зависит от того, опубликовано ли изменение:

- незакоммиченное изменение можно исправить в working tree;
- последний локальный commit можно дополнить или переписать;
- опубликованный commit безопаснее отменять новым `revert` commit;
- потерянные локальные commits часто можно найти через reflog.

Перед любой отменой нужно проверить текущую ветку, status и diff.

## Bash: модель выполнения

Shell запускает процессы и соединяет их стандартные потоки:

- stdin — вход;
- stdout — обычный вывод;
- stderr — диагностический вывод;
- exit code — `0` для успеха, ненулевой для ошибки.

Pipe передаёт stdout одной команды в stdin другой. Redirect направляет поток в файл или меняет источник ввода. Эти механизмы позволяют собирать небольшие инструменты в pipeline.

### Quoting

Пробелы и специальные символы интерпретируются shell. Обычно переменную с путём или пользовательским значением заключают в двойные кавычки. Одинарные кавычки запрещают подстановки, двойные допускают `$variable`.

Скрипт должен:

- проверять обязательные аргументы;
- явно реагировать на ошибки;
- использовать понятные exit codes;
- не выводить секреты;
- аккуратно работать с временными файлами;
- не выполнять разрушительные команды по неразрешённому пути.

## Docker: image и container

Docker image — неизменяемый набор слоёв. Container — процесс с изолированными namespaces, ограничениями ресурсов и writable layer поверх image. Контейнеры используют ядро host-системы, поэтому они легче виртуальных машин.

Dockerfile описывает сборку. Порядок инструкций влияет на cache: редко меняющиеся зависимости размещают раньше часто меняющегося исходного кода. Для Go используют multi-stage build, чтобы compiler не попадал в production image.

Минимальные свойства production image:

- фиксируемая версия base image;
- небольшой состав файлов;
- запуск не от root;
- конфигурация через окружение или подключённые secrets;
- корректная обработка сигналов;
- отсутствие исходных секретов в layers;
- понятный healthcheck на уровне платформы.

## Сеть и данные контейнера

Внутри контейнера `localhost` указывает на сам контейнер. Сервисы одной container network находят друг друга по DNS-имени. Публикация порта связывает порт host с портом контейнера.

Writable layer временный. Постоянные данные хранят в volume или внешнем сервисе. Контейнер приложения должен быть заменяемым: после удаления новый экземпляр восстанавливает работу из конфигурации и внешних данных.

## CI

Минимальный pipeline Go-сервиса обычно включает:

1. форматирование и lint;
2. сборку;
3. unit-тесты;
4. integration-тесты;
5. проверку race или безопасности по политике проекта;
6. сборку image;
7. публикацию однозначно версионированного artifact.

Проверки должны быть воспроизводимыми. Один и тот же commit должен приводить к одному идентифицируемому artifact. Production не стоит собирать повторно из другой версии исходников.

## CD и безопасный deploy

Deployment доставляет версию в окружение, release открывает функцию пользователям. Стратегии:

- rolling update — экземпляры заменяются постепенно;
- blue-green — трафик переключается между двумя окружениями;
- canary — новая версия получает небольшую долю трафика;
- feature flag — функциональность включается отдельно от deploy.

Во время rollout следят за errors, latency, ресурсами и бизнес-показателями. Нужен быстрый rollback и совместимость приложения со схемой БД во время смешанной работы старой и новой версий.

## Graceful shutdown

После `SIGTERM` сервис должен:

1. перестать считаться готовым к новому трафику;
2. прекратить приём новой работы;
3. завершить активные операции в пределах deadline;
4. остановить consumers и согласовать offsets;
5. закрыть соединения и завершиться.

Graceful shutdown ограничен временем. Зависшие операции должны отменяться через context или другой механизм отмены.
