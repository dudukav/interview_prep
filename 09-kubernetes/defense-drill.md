# Тренажёр защиты SRE: Kubernetes и эксплуатационные сценарии

Здесь вопросы сформулированы так, как их часто задают на защите: преподаватель указывает на конкретный объект в манифесте и спрашивает не определение, а последствия отказа. Хороший ответ строится в порядке:

1. **Роль компонента** именно в этой системе.
2. **Что произойдёт при отказе** сразу и после исчерпания буферов/таймаутов.
3. **Что увидят пользователь и оператор**: симптомы, метрики, события, логи.
4. **Как система восстановится** и возможна ли потеря данных.
5. **Какие меры снижают риск**.

Не стоит обещать «ничего не случится», пока не названы controller, источник данных, тип буфера, режим доставки и общие зависимости.

## Словарь терминов

Ниже не буквальный перевод, а значение термина в контексте Kubernetes и SRE. На защите нормально произносить английский термин, но полезно сразу раскрывать его смысл: например, «`backpressure`, то есть замедление приёмника распространяется назад к источнику».

### Базовые понятия Kubernetes

| Термин | Перевод и смысл |
|---|---|
| **SRE — Site Reliability Engineering** | Инженерия надёжности: применение инженерных и программных методов для доступности, производительности и предсказуемой эксплуатации системы. |
| **cluster** | Кластер — совокупность машин и компонентов Kubernetes, управляемых как одна система. |
| **node** | Узел — физическая или виртуальная машина кластера, на которой запускаются Pod. |
| **control plane** | Управляющая часть кластера: принимает изменения, хранит состояние, планирует Pod и запускает controllers. |
| **workload** | Полезная нагрузка: приложение или задача, запущенная в Kubernetes. Deployment, StatefulSet и DaemonSet — workload-объекты. |
| **container** | Изолированный process с упакованными приложением и зависимостями. Контейнер запускается внутри Pod. |
| **Pod** | Минимальная единица запуска в Kubernetes. Контейнеры одного Pod делят сеть и могут делить volumes. Pod временный: после пересоздания его имя и IP могут измениться. |
| **manifest** | YAML-описание желаемого Kubernetes-объекта. |
| **API — Application Programming Interface** | Программный интерфейс. В Kubernetes все изменения ресурсов проходят через API server. |
| **`kubectl`** | Командная утилита для обращения к Kubernetes API: посмотреть, создать, изменить или удалить объект. |
| **kubelet** | Агент Kubernetes на каждой node: получает PodSpec и через container runtime обеспечивает запуск контейнеров. |
| **container runtime** | Программа, непосредственно запускающая контейнеры на node, например containerd или CRI-O. |
| **image** | Неизменяемый шаблон filesystem и метаданных, из которого запускают container. |
| **filesystem** | Файловая система: представление файлов и каталогов внутри контейнера или на node. |
| **desired state / actual state** | Желаемое и фактическое состояния. Например, желаемое — три Pod, фактическое — два; controller постарается создать третий. |
| **controller** | Управляющий цикл, который сравнивает desired и actual state и устраняет различие. |
| **reconciliation loop** | Постоянное согласование состояния: observe → compare → act, то есть «посмотреть → сравнить → исправить». |
| **replica** | Отдельный экземпляр приложения, обычно отдельный Pod. Несколько replicas повышают пропускную способность и могут повысить доступность. |
| **Deployment** | Controller для обычно stateless-приложений. Управляет replicas и постепенным обновлением Pod через ReplicaSet. |
| **ReplicaSet** | Поддерживает заданное число одинаковых Pod. Обычно создаётся и управляется Deployment. |
| **StatefulSet** | Controller для экземпляров с устойчивыми именами, порядком запуска и отдельными volumes. Сам по себе не настраивает репликацию данных БД. |
| **DaemonSet** | Controller, который поддерживает по Pod на каждой подходящей node. Типичные примеры: сборщик логов, сетевой или monitoring agent. |
| **stateless / stateful** | Stateless не хранит необходимое состояние локально между запросами; stateful владеет состоянием, которое требуется сохранять и согласовывать. |
| **namespace** | Логическая область имён и разграничения ресурсов внутри кластера. Это не отдельный кластер и не полная граница безопасности. |
| **label** | Метка `key=value` на объекте, используемая для группировки и выбора. |
| **selector** | Условие выбора объектов по labels. Например, Service находит свои Pod через selector. |
| **annotation** | Дополнительные метаданные объекта, не предназначенные для выбора через selector. |
| **Pod template / `.spec.template`** | Шаблон будущих Pod внутри workload. Его изменение создаёт новую ревизию Deployment/StatefulSet и запускает rollout. |
| **operator** | Kubernetes-controller, который знает правила эксплуатации конкретной сложной системы, например PostgreSQL: bootstrap, replication, failover и backup. |
| **Reloader** | Сторонний controller, способный запустить rollout workload после изменения связанного ConfigMap или Secret. Это не встроенное поведение Kubernetes. |

### Размещение, ресурсы и жизненный цикл

| Термин | Перевод и смысл |
|---|---|
| **scheduler / scheduling** | Планировщик / планирование: выбор node для ещё не размещённого Pod. |
| **nodeSelector** | Простое требование запускать Pod только на nodes с указанными labels. |
| **affinity / anti-affinity** | Правила «размещать рядом» / «размещать раздельно» относительно nodes или других Pod. |
| **taint / toleration** | Taint отталкивает Pod от node, toleration разрешает конкретному Pod эту node использовать; это разрешение, а не обязательное назначение. |
| **topology constraint** | Ограничение распределения Pod по доменам отказа: nodes, zones и другим topology keys. |
| **request** | Запрашиваемый ресурс CPU/memory. Scheduler использует его при выборе node. |
| **limit** | Верхняя граница ресурса: превышение memory limit может привести к OOM kill, CPU limit — к throttling. |
| **CPU throttling** | Принудительное замедление процесса при достижении CPU limit. |
| **OOM / OOMKilled** | Out Of Memory: памяти не хватило, и process был завершён ядром или из-за memory limit контейнера. |
| **QoS — Quality of Service** | Класс приоритета Pod при дефиците ресурсов, вычисляемый из requests и limits. |
| **Pending** | Pod принят API, но ещё не запущен: например, scheduler не нашёл node или PVC не подключён. |
| **Running** | Контейнеры Pod запущены или запускаются. Это не означает, что приложение готово принимать трафик. |
| **Ready / NotReady** | Готов / не готов получать новый трафик через Service. Определяется readiness probe и состоянием Pod. |
| **probe** | Периодическая проверка контейнера со стороны kubelet. |
| **readiness probe** | Проверяет готовность принимать трафик. Ошибка убирает Pod из endpoints, но не перезапускает container. |
| **liveness probe** | Проверяет, нужно ли перезапустить зависший container. Ошибка приводит к restart. |
| **startup probe** | Даёт медленно запускающемуся приложению время до включения liveness/readiness. |
| **graceful shutdown** | Корректное завершение: перестать принимать новую работу, закончить текущую и закрыть ресурсы до `SIGKILL`. |
| **eviction** | Вытеснение Pod с node, например при `drain` или нехватке ресурсов. |
| **drain** | Подготовка node к обслуживанию: запрет новых Pod и безопасное вытеснение допустимых существующих. |
| **PDB — PodDisruptionBudget** | Ограничивает недоступность replicas при добровольных disruptions. От падения node и всех видов удаления не защищает. |
| **rollout** | Постепенное развёртывание новой версии Pod template. |
| **rollback** | Возврат к предыдущей версии Pod template. Автоматически не откатывает схему или данные БД. |
| **`maxSurge`** | Сколько дополнительных Pod сверх желаемого числа разрешено создать во время rollout. |
| **`maxUnavailable`** | Сколько Pod может быть недоступно во время rollout. |
| **HPA — Horizontal Pod Autoscaler** | Автоматически меняет число replicas по CPU, memory или другим метрикам. |
| **scale-out / scale-down** | Добавление / удаление экземпляров приложения. Scale-up иногда используют для увеличения ресурсов одной машины. |

### Service и сеть

| Термин | Перевод и смысл |
|---|---|
| **Service** | Стабильная точка доступа к меняющемуся набору ready Pod. Выбирает Pod по labels. |
| **endpoint** | Конкретный адрес и порт Pod, на который Service может направить соединение. |
| **EndpointSlice** | Kubernetes-объект с группой endpoints Service; более масштабируемая замена старому объекту Endpoints. |
| **DNS — Domain Name System** | Разрешает имена Service в IP-адреса внутри кластера. |
| **CNI — Container Network Interface** | Стандарт и плагины, которые организуют сеть Pod и часто реализуют NetworkPolicy. |
| **NetworkPolicy** | Правила, каким Pod разрешено обмениваться сетевым трафиком. Работают только при поддержке CNI. |
| **dataplane** | Компоненты и правила, через которые фактически проходит трафик, в отличие от управляющего control plane. |
| **L7 — Layer 7** | Прикладной уровень сети, например HTTP/gRPC; L7 proxy умеет маршрутизировать по host/path и содержимому протокола. |
| **keep-alive** | Повторное использование уже открытого соединения для нескольких запросов. Может делать распределение между Pod неравномерным. |
| **session affinity** | Закрепление запросов одного клиента за одним endpoint, например по client IP. Может ухудшить равномерность нагрузки. |
| **timeout** | Максимальное время ожидания операции, после которого она считается неуспешной. |
| **retry** | Повтор неуспешной операции. Без ограничений и проверки идемпотентности может усилить аварию или продублировать действие. |
| **connection draining** | Прекращение приёма новых соединений с ожиданием завершения уже открытых перед остановкой Pod. |
| **fallback** | Запасной путь при сбое основного: например, прочитать данные из старого shard, если в новом их ещё нет. |

### Конфигурация и хранилище

| Термин | Перевод и смысл |
|---|---|
| **ConfigMap** | Kubernetes-объект для несекретной конфигурации. |
| **Secret** | Kubernetes-объект для чувствительных данных. Нуждается в RBAC и защите хранилища; base64 не является шифрованием. |
| **environment variable / env** | Переменная окружения process. Её значение фиксируется при запуске и само не обновляется. |
| **volume / mount** | Volume предоставляет данные Pod, mount подключает их по пути внутри контейнера. |
| **PV — PersistentVolume** | Ресурс постоянного хранилища, предоставленный кластеру. |
| **PVC — PersistentVolumeClaim** | Запрос приложения на постоянное хранилище нужного размера и класса. |
| **StorageClass** | Описывает тип хранилища и способ динамического создания PV. |
| **CSI — Container Storage Interface** | Стандарт подключения storage-драйверов к Kubernetes. |
| **access mode** | Допустимый режим подключения volume, например `ReadWriteOnce` — запись с одной node. Это не означает строгую защиту от всех вторых writers. |
| **`emptyDir`** | Временный volume на время жизни Pod. Переживает restart контейнера, но удаляется вместе с Pod. |
| **`hostPath`** | Подключение каталога конкретной node в Pod. Привязывает данные к node и требует осторожности с безопасностью. |
| **reclaim policy** | Что делать с PV после удаления PVC: удалить backing storage (`Delete`) или оставить для ручного восстановления (`Retain`). |
| **WAL — Write-Ahead Log** | Журнал предварительной записи: изменения сначала фиксируются в журнале, что помогает восстановлению и репликации. |
| **backup / restore** | Резервная копия / восстановление. Наличие PVC или replicas не заменяет проверенный backup. |
| **zonal volume** | Диск, доступный только в определённой зоне; Pod нельзя произвольно перенести с ним в другую zone. |
| **fencing** | Гарантированное отключение старого владельца ресурса, чтобы два экземпляра одновременно не считали себя primary и не портили данные. |
| **lease** | Ограниченная по времени «аренда» права быть владельцем/leader; её нужно регулярно продлевать. |

### База данных и распределённые данные

| Термин | Перевод и смысл |
|---|---|
| **latency / throughput** | Задержка одной операции / число операций за единицу времени. Низкая latency и высокий throughput — разные характеристики. |
| **connection pool** | Ограниченный набор переиспользуемых соединений с БД. |
| **connection budget** | Безопасный общий лимит соединений, распределённый между replicas и служебными клиентами. |
| **N+1 query problem** | Один запрос получает список, затем отдельный запрос выполняется для каждого элемента; число запросов и нагрузка резко растут. |
| **primary / read replica** | Primary принимает записи; read replica копирует его данные и обслуживает чтения, обычно с некоторым отставанием. |
| **replication lag** | Отставание replica от primary по времени или объёму ещё не применённых изменений. |
| **read-after-write consistency** | Гарантия, что сразу после своей записи клиент при чтении уже увидит результат. Чтение с отстающей replica может её нарушить. |
| **lock** | Блокировка, защищающая данные от конфликтующих операций; ожидание locks увеличивает latency. |
| **batch** | Пакетная обработка нескольких элементов одной операцией для уменьшения накладных расходов. |
| **rate limit** | Ограничение количества операций за период, защищающее систему и зависимости от перегрузки. |
| **cache invalidation** | Обновление или удаление устаревших данных из кэша после изменения источника истины. |
| **TTL — Time To Live** | Время жизни записи, после которого она истекает. |
| **cache stampede** | Одновременный промах множества клиентов по одному истёкшему ключу и лавина запросов в БД. |
| **singleflight / request coalescing** | Объединение одинаковых одновременных запросов: один выполняет работу, остальные ждут его результат. |
| **shard / sharding** | Часть данных / горизонтальное разделение данных между несколькими узлами. |
| **shard key** | Поле или функция, определяющая, в какой shard попадёт запись. |
| **resharding** | Изменение распределения данных между shards, часто при добавлении или удалении узлов. |
| **consistent hashing** | Схема хеширования, при которой изменение числа узлов перемещает только часть ключей, а не почти все данные. |
| **hot key / hot shard** | Ключ или shard с непропорционально большой нагрузкой. Равный объём данных не гарантирует равную нагрузку. |
| **dual write** | Временная запись одного изменения одновременно в старое и новое хранилище. Нужны обработка частичного успеха и идемпотентность. |
| **backfill** | Фоновое копирование уже существующих исторических данных в новую схему или shard. |
| **CDC — Change Data Capture** | Передача потока изменений БД, позволяющая догнать новые записи во время backfill. |
| **checkpoint** | Сохранённая позиция прогресса, с которой миграцию или чтение можно продолжить после сбоя. |
| **checksum** | Контрольная сумма для проверки, что набор данных при копировании не изменился. |
| **checksum annotation** | Аннотация Pod template с хешем ConfigMap/Secret. При изменении данных меняется хеш, а значит начинается rollout. |
| **hash / hash function** | Хеш / хеш-функция: преобразование ключа в число фиксированного размера; используется, например, для выбора shard. |
| **idempotency** | Свойство операции, при котором безопасный повтор не меняет результат после первого успешного выполнения. |
| **quorum** | Минимальное число участников, необходимое для согласованного решения или доступности операции. |
| **PgBouncer** | Лёгкий pooler для PostgreSQL: принимает множество клиентских соединений и переиспользует меньшее число соединений с БД. |
| **backward-compatible migration** | Обратно совместимая миграция: старый и новый код могут временно работать с новой схемой одновременно. |
| **expand → migrate → contract** | Сначала добавить новую структуру без удаления старой, затем перенести код/данные, и только после этого удалить устаревшую структуру. |

### Vector, логи и отказоустойчивость

| Термин | Перевод и смысл |
|---|---|
| **agent / collector** | Агент / сборщик, который читает телеметрию, обрабатывает и отправляет её дальше. Vector может выполнять обе роли. |
| **source / transform / sink** | Источник данных / преобразование / получатель. В Vector это три основных типа компонентов pipeline. |
| **pipeline** | Цепочка движения данных от source через transforms к одному или нескольким sinks. |
| **buffer** | Ограниченное промежуточное хранилище событий, пока sink не успевает их принять. |
| **memory buffer / disk buffer** | Буфер в RAM быстрый, но теряется при crash; дисковый медленнее, зато может пережить restart. |
| **backlog** | Накопившаяся очередь ещё не обработанных или не отправленных событий. |
| **retryable failure** | Ошибка, после которой отправку имеет смысл повторить, например timeout, HTTP 429 или многие ответы 5xx. |
| **backoff** | Увеличивающаяся пауза между повторными попытками, чтобы не добивать сломанную зависимость. |
| **jitter** | Случайная добавка к паузе retry, чтобы множество агентов не повторяли запрос одновременно. |
| **backpressure** | Обратное давление: медленный sink заполняет buffer и заставляет предыдущие стадии и source замедлиться. |
| **`when_full: block`** | При полном buffer ждать свободного места и распространять backpressure; новые события намеренно не отбрасываются на этом шаге. |
| **`when_full: drop_newest`** | При полном buffer отбрасывать новые события, сохраняя скорость работы ценой потери данных. |
| **acknowledgement / ack** | Подтверждение, что событие принято или надёжно сохранено на определённом участке pipeline. |
| **at-most-once** | Событие доставляется не более одного раза, но может потеряться. |
| **at-least-once** | Событие должно быть доставлено хотя бы один раз, но возможны дубликаты. Требует идемпотентной обработки или дедупликации. |
| **exactly-once** | Каждое логическое событие влияет на результат ровно один раз. Сквозная гарантия сложна и не появляется только от retries. |
| **log rotation** | Закрытие/переименование старого log-файла и создание нового, чтобы логи не росли бесконечно. Непрочитанный файл могут удалить по retention policy. |
| **retention** | Срок или объём хранения данных до автоматического удаления. |
| **garbage collection / cleanup** | Автоматическая очистка ненужных images, containers, файлов или других ресурсов для освобождения места. |
| **DiskPressure** | Состояние node с опасно малым свободным местом; kubelet может начать cleanup и eviction Pod. |
| **load shedding** | Осознанный отказ от части работы или низкоприоритетных данных для сохранения основной функции системы. |
| **thundering herd** | «Стадо»: множество клиентов одновременно повторяют запросы или выгружают backlog после восстановления зависимости. |
| **durability** | Устойчивость данных к crash/restart и сбоям носителя. |
| **VictoriaLogs** | Система хранения и поиска логов семейства VictoriaMetrics; Vector выступает отправителем, VictoriaLogs — sink/backend. |
| **backend / downstream** | Backend — обслуживающая система за интерфейсом; downstream — следующий зависимый компонент по ходу потока данных. |

## Вопросы, которые уже встречались на защите

### 1. Что это за DaemonSet, зачем он здесь и что будет, если его удалить?

**Короткий ответ:** DaemonSet обеспечивает по одному Pod на каждой подходящей node. Здесь он нужен, например, чтобы Vector локально читал container logs с каждой node. Если удалить один его Pod, controller создаст замену. Если удалить сам DaemonSet, агенты исчезнут и новые логи с этих nodes перестанут собираться; уже запущенные приложения обычно продолжат работать.

**Важно уточнить на защите:**

- «Удалить Pod» и «удалить DaemonSet» — разные эксперименты.
- DaemonSet запускается не обязательно на всех nodes: влияют `nodeSelector`, affinity, taints/tolerations и scheduling.
- При `kubectl delete daemonset vector` зависимые Pod обычно удалятся каскадно. С `--cascade=orphan` Pod могут остаться, но controller больше не будет их восстанавливать и обновлять.
- Последствие зависит от роли: удаление log collector создаст дыру в логах; удаление CNI-компонента или `kube-proxy` может нарушить сеть; удаление security agent снизит контроль.

**Что проверить:**

```bash
kubectl describe daemonset vector -n observability
kubectl get pods -n observability -o wide
kubectl get daemonset vector -n observability \
  -o jsonpath='{.status.desiredNumberScheduled}/{.status.numberReady}{"\n"}'
```

**Типичное добивание:** «А почему не Deployment?» — агенту нужен локальный доступ к логам и filesystem каждой node, а масштаб Deployment не гарантирует Pod на каждой node.

### 2. Мы увеличили число replicas Deployment. Как теперь снять нагрузку с БД?

**Короткий ответ:** масштабирование stateless-приложения само по себе не масштабирует БД и иногда делает хуже: новые Pod открывают больше соединений и повышают параллелизм запросов. Сначала надо определить узкое место по latency, throughput, CPU/IO, locks, slow queries и числу connections, а затем выбрать меру.

Возможные меры:

- исправить N+1 и тяжёлые запросы, добавить подходящие индексы;
- ограничить pool на каждом Pod и общий connection budget; поставить PgBouncer;
- кэшировать часто читаемые данные с понятными TTL и invalidation;
- вынести допустимые чтения на read replicas с учётом replication lag;
- объединять записи в batch, убирать синхронную работу в очередь;
- ввести rate limit, backpressure и деградацию необязательных функций;
- партиционировать или шардировать данные, если одной машине действительно тесно.

**Формула для ответа:** если у каждого из `N` Pod pool до `P` соединений, потенциальный максимум — примерно `N × P` плюс служебные клиенты. Он не должен превышать безопасный бюджет БД.

**Типичное добивание:** «Давайте просто добавим read replica?» — она помогает только чтениям, которые допустимо обслуживать с отставанием; writes, блокировки primary и read-after-write consistency она не исправит.

### 3. Мы поменяли Secret. Обновятся ли Deployment и StatefulSet?

**Короткий ответ:** сами workload-объекты не сделают rollout только из-за изменения Secret. Дальше всё зависит от способа подключения:

- значения из Secret, переданные через environment variables, в уже работающем process не изменятся;
- файлы из Secret volume обычно обновляются kubelet асинхронно, не мгновенно; приложение должно уметь перечитать файл;
- mount через `subPath` автоматически не обновляется;
- StatefulSet ведёт себя в этом отношении так же, как Deployment.

Для предсказуемой ротации делают явный rollout, меняют checksum-аннотацию Pod template или используют controller вроде Reloader. При этом нужно учитывать порядок ротации: некоторое время старые и новые credentials могут использоваться одновременно. Для пароля БД безопаснее сначала разрешить новый credential, обновить клиентов, убедиться в rollout и только затем отозвать старый.

```bash
kubectl rollout restart deployment/api -n shop
kubectl rollout status deployment/api -n shop
kubectl rollout restart statefulset/worker -n shop
```

**Типичное добивание:** «Почему checksum работает?» — изменение annotation внутри `.spec.template` меняет Pod template hash, поэтому controller создаёт новую ревизию Pod.

### 4. Зачем здесь PVC?

**Короткий ответ:** PVC — запрос workload на persistent storage с нужными размером, access mode и StorageClass. Он отделяет приложение от конкретного диска/PV и позволяет Pod после пересоздания снова подключить постоянные данные.

Нужно уметь назвать, **какие именно данные** здесь должны пережить Pod: данные БД, очередь на диске, WAL или disk buffer Vector. Если это cache или временные файлы, возможно, хватит `emptyDir`.

PVC не гарантирует сам по себе:

- backup и восстановление;
- репликацию между зонами;
- одновременный mount на нескольких nodes — это зависит от access mode и CSI;
- сохранность после удаления PVC — важны reclaim policy PV и настройки StorageClass.

Для StatefulSet `volumeClaimTemplates` обычно создаёт отдельный PVC на каждую replica. Поэтому replicas не должны бездумно писать в один `ReadWriteOnce` volume.

**Типичное добивание:** «Что будет при удалении Pod?» — PVC обычно останется, новый Pod сможет подключить его. «А при удалении PVC?» — возможна потеря данных; результат зависит от `persistentVolumeReclaimPolicy: Retain/Delete` и storage backend.

### 5. Как бы ты делал решардинг?

**Короткий ответ:** решардинг — перенос диапазонов/ключей между shards при изменении topology. Сначала выбираю стабильный shard key и проверяю равномерность, locality запросов и отсутствие hot keys. Онлайн-миграцию делаю поэтапно: создать новую topology, копировать исторические данные, синхронизировать новые изменения, переключить чтения, проверить консистентность и только потом убрать старое размещение.

Что обязательно обсудить:

- consistent hashing уменьшает объём перемещений при изменении числа shards, но не лечит hot key;
- dual write требует идемпотентности и механизма восстановления после частичного успеха;
- backfill не должен вытеснить production-трафик по CPU/IO/network;
- во время миграции нужны checkpoints, сверка counts/checksums и возможность отката;
- запросы по нескольким shards дороже и сложнее для сортировки, агрегации и транзакций;
- routing/config version должна обновляться согласованно у клиентов.

**Типичное добивание:** «Что будет с запросом во время переноса ключа?» — нужен явно выбранный протокол: временное чтение из нового с fallback в старый, dual write/CDC либо короткая блокировка диапазона. Просто поменять hash function недостаточно.

### 6. Vector отправляет логи в VictoriaLogs. Что будет, если VictoriaLogs недоступна?

**Короткий ответ:** Vector получит ошибки/таймауты и для retryable failures будет повторять отправку с backoff. События тем временем попадут в buffer sink. Дальнейшее поведение определяется конфигурацией buffer:

- memory buffer быстрый, но потеряется при рестарте Vector;
- disk buffer переживает restart лучше и позволяет приблизиться к at-least-once доставке;
- при полном buffer и `when_full: block` backpressure пойдёт вверх по pipeline;
- при `when_full: drop_newest` новые события начнут теряться;
- после восстановления накопившийся backlog может создать резкий поток в VictoriaLogs и конкурировать с новыми логами.

Если Vector читает container log-файлы на node, backpressure не останавливает приложение: файлы продолжат расти и могут быть ротированы раньше, чем Vector их прочитает. При переполнении диска пострадает уже node. Поэтому нужны disk buffer/PVC или гарантированный локальный диск, лимиты, мониторинг заполнения и разумная политика потери низкоприоритетных логов.

Пример направления конфигурации, а не универсальные значения:

```yaml
sinks:
  vlogs:
    type: elasticsearch
    inputs: [parse_logs]
    endpoints: [http://victoria-logs:9428/insert/elasticsearch/]
    buffer:
      type: disk
      max_size: 1073741824 # подобрать по log rate и допустимому outage
      when_full: block
```

Размер оценивают как `пиковый объём логов в секунду × допустимое время простоя × запас`. Проверять надо internal metrics Vector: ошибки запросов, retries, dropped events, заполнение/размер buffer и lag чтения source, а также свободное место node/PVC.

**Гарантия:** disk buffer + acknowledgements дают at-least-once, то есть возможны дубликаты. Без проверки конкретных source и sink нельзя обещать exactly-once или полное отсутствие потерь.

## Похожие сценарные вопросы

### Workloads и scheduling

#### 7. Чем удаление Pod отличается от его eviction и падения node?

При обычном удалении controller создаст замену, а kubelet может выполнить graceful shutdown. Eviction может быть добровольным (`drain`) или из-за resource pressure; PDB ограничивает только некоторые добровольные disruptions. При потере node control plane ждёт и затем создаёт Pod в другом месте, но старый процесс при сетевом разделении может ещё жить — для stateful-систем важны fencing и lease.

#### 8. Что будет с DaemonSet при добавлении новой node?

Controller создаст на подходящей node новый Pod. До его готовности на node может не быть логов/метрик/security coverage. Проверяют tolerations, особенно для control-plane nodes, и готовность агента до допуска прикладной нагрузки.

#### 9. Почему Pod `Pending`, хотя на nodes «ещё есть память»?

Scheduler смотрит на requests, а не текущую фактическую утилизацию. Причинами также бывают taints, affinity, topology constraints, quota, max pods на node и неготовый PVC. Ответ ищут в Events у Pod.

#### 10. Что произойдёт, если requests не заданы, а limits заданы неправильно?

Планирование и QoS станут менее предсказуемыми. Маленький memory limit даст OOMKilled, маленький CPU limit — throttling и рост latency. Без адекватных requests scheduler может уплотнить node сильнее, чем выдержит реальная нагрузка.

#### 11. Зачем PDB, и спасёт ли он при падении node?

PDB ограничивает число одновременно недоступных replicas при добровольных disruption, например `drain`. Он не предотвращает аппаратный отказ, OOM, удаление Deployment или неудачный rollout и может мешать обслуживанию, если capacity недостаточна.

### Rollout, probes и конфигурация

#### 12. Rollout завис: новый Pod Running, но Deployment не обновляется. Почему?

`Running` не равно `Ready`. Проверяю readiness, `minReadySeconds`, image/config, capacity для `maxSurge`, quota и events. Не ослабляю probe до выяснения причины: иначе плохой Pod попадёт в Service.

#### 13. Что будет, если liveness probe проверяет БД?

При сбое БД все replicas могут одновременно начать перезапускаться, усилить нагрузку reconnect-штормом и потерять диагностический контекст. Liveness должна отвечать, способен ли сам process восстановиться без restart; зависимость чаще отражают в readiness с осторожной политикой или в отдельной метрике.

#### 14. Можно ли откатить Deployment после несовместимой миграции БД?

Kubernetes откатит Pod template, но не схему и данные БД. Миграции делают backward-compatible: expand → deploy совместимого кода → backfill → switch → contract. Иначе rollback приложения может перестать работать со новой схемой.

#### 15. Изменили ConfigMap, но приложение видит старое значение. Где искать?

Сначала выясняю способ доставки: env не обновится, `subPath` не обновится, volume обновляется с задержкой, а приложение может кэшировать файл. Сравниваю объект в API, содержимое внутри Pod и фактически загруженную конфигурацию; затем выполняю контролируемый rollout.

#### 16. Что будет при `maxUnavailable: 0` и `maxSurge: 0`?

Rolling update не сможет начать замену: нельзя ни убрать старый Pod, ни создать дополнительный. Параметры должны оставлять хотя бы один возможный шаг и учитывать quota/capacity.

### Service и сеть

#### 17. Pod отвечает по IP, но Service не работает. Что проверять?

Selector и labels, EndpointSlice, readiness, соответствие `port/targetPort`, namespace, слушает ли process на `0.0.0.0`, затем NetworkPolicy, DNS и dataplane. Проверка напрямую по Pod IP обходит часть этого пути и не доказывает исправность Service.

#### 18. Все replicas есть, но трафик распределяется неравномерно. Почему?

Service обычно балансирует соединения, а не отдельные HTTP-запросы. Keep-alive, HTTP/2, долгие gRPC streams и session affinity закрепляют много работы за одним endpoint. Нужны метрики на Pod, корректное client-side поведение и иногда L7 proxy или дробление долгих соединений.

#### 19. Что произойдёт с существующим соединением, когда Pod станет NotReady?

Readiness уберёт endpoint для новых соединений, но не обязана разорвать уже установленные. Клиенту нужны timeouts, retry только безопасных/idempotent операций и connection draining на стороне приложения/proxy.

### Storage и stateful workloads

#### 20. Можно ли увеличить replicas StatefulSet с БД с 1 до 3?

Kubernetes создаст ещё два Pod и, вероятно, два PVC, но данные автоматически не реплицирует. Нужны поддерживаемые самой БД bootstrap, replication, membership, quorum, failover и backup/restore; обычно этим управляет operator.

#### 21. Pod с PVC застрял на другой node. Почему?

Volume может быть zonal или `ReadWriteOnce` и всё ещё attached к старой node. Проверяю PV/PVC, VolumeAttachment, topology и CSI events. Нельзя форсировать второй writer без понимания fencing: можно повредить данные.

#### 22. Чем `emptyDir` отличается от PVC для буфера Vector?

`emptyDir` переживает restart контейнера, но исчезает вместе с Pod. PVC или устойчивый host disk может сохранить backlog после пересоздания Pod, но требует capacity, cleanup и привязки к node/topology. Выбор зависит от допустимого окна потери логов.

### Масштабирование и зависимости

#### 23. Почему HPA может ухудшить ситуацию при медленной БД?

Рост latency/CPU может вызвать scale-out, новые Pod добавят соединения и запросы, а БД станет ещё медленнее — положительная обратная связь. Нужны connection budget, concurrency limits, backpressure и метрики насыщения зависимости; иногда масштабирование надо временно ограничить.

#### 24. По какой метрике масштабировать consumer?

CPU подходит не всегда. Чаще полезны lag/возраст старейшего сообщения и время обработки с учётом partitions и пропускной способности downstream. Replicas сверх числа partitions могут простаивать, а агрессивный scale-down вызвать rebalance и повторную обработку.

#### 25. Кэш снял нагрузку с БД. Что нового может сломаться?

Появляются stale data, cache stampede, hot keys, eviction и новая общая зависимость. Нужны TTL с jitter, request coalescing/singleflight, лимиты, fallback и наблюдаемость hit rate/latency/errors. Кэш нельзя считать источником истины без отдельного решения.

### Наблюдаемость и отказ VictoriaLogs

#### 26. Как понять, что Vector перестал доставлять логи, если сами ошибки Vector тоже уходят в VictoriaLogs?

Нужен независимый канал: scrape internal metrics Vector через Prometheus, alert на send errors/dropped events/buffer utilization и локальные stderr/journald. Проверка только поиском логов в сломанном backend создаёт слепую зону.

#### 27. VictoriaLogs восстановилась. Почему её снова «положил» Vector?

Все агенты одновременно начали выгружать backlog, создав thundering herd. Ограничивают concurrency/rate, используют backoff с jitter, capacity planning и поэтапное восстановление; следят, чтобы ingest backlog не вытеснял свежие данные бесконечно.

#### 28. Можно ли гарантировать отсутствие потери логов?

Не абсолютным утверждением. Нужно пройти весь путь: запись приложения, container runtime и rotation, чтение source, acknowledgements, buffer, durability диска, retries и приём sink. At-least-once допускает дубликаты; при полном конечном storage всё равно нужен выбор между backpressure и потерей.

#### 29. Что будет, если disk buffer Vector заполнит диск node?

Node получит DiskPressure, kubelet начнёт garbage collection и eviction, а приложения могут потерять возможность писать данные. Для buffer задают размер меньше доступного бюджета, отдельный volume/partition, alerts и политику поведения при заполнении.

#### 30. Vector запущен DaemonSet. Нужен ли ему PVC?

Не всегда. Per-Pod PVC у DaemonSet сложнее сопоставить с конкретной node; часто используют контролируемый `hostPath`/локальный volume для node-local buffer либо memory buffer, осознанно принимая риск. В managed-среде PVC может быть оправдан, если CSI/topology и lifecycle гарантируют нужное поведение. Главное — объяснить требование к durability, а не выбирать storage по шаблону.
