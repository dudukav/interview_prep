# Простая шпаргалка к защите SRE

Начни с этого файла. Ответы здесь специально короткие. Сначала научись объяснять их своими словами, а потом переходи к [подробному тренажёру](defense-drill.md).

## Самые нужные слова

| Слово | Простое значение |
|---|---|
| **Kubernetes** | Система, которая запускает приложения на нескольких серверах и следит, чтобы они продолжали работать. |
| **node** | Сервер внутри Kubernetes. |
| **Pod** | Запущенный экземпляр приложения. Если Pod удалить, Kubernetes обычно создаст новый. |
| **container** | Изолированный процесс с приложением. Контейнер работает внутри Pod. |
| **replica** | Одна копия приложения. Три replicas — три Pod с этим приложением. |
| **Deployment** | Объект для запуска нескольких одинаковых Pod приложения. Подходит для сервисов без важных локальных данных. |
| **StatefulSet** | Объект для приложений, которым нужны постоянное имя и свой диск. Часто применяется для баз данных. |
| **DaemonSet** | Объект, который запускает по одному Pod на каждом сервере. |
| **Service** | Постоянный адрес, через который запросы попадают в подходящие Pod. |
| **Secret** | Объект для паролей, токенов и других секретных значений. |
| **volume** | Диск или каталог, подключённый к Pod. |
| **PV** | Сам постоянный диск в Kubernetes. |
| **PVC** | Запрос приложения на постоянный диск. |
| **rollout** | Постепенный перезапуск Pod с новой версией или настройками. |
| **readiness probe** | Проверка: можно ли уже отправлять запросы в Pod. |
| **liveness probe** | Проверка: не зависло ли приложение и не нужно ли его перезапустить. |
| **buffer** | Временное место, куда складываются данные, пока получатель недоступен или работает медленно. |
| **retry** | Повторная попытка выполнить неуспешную операцию. |
| **backoff** | Пауза между повторными попытками. Обычно пауза постепенно увеличивается. |
| **backpressure** | Если получатель не справляется, отправитель тоже замедляет приём новых данных. |

## Шесть главных вопросов

### 1. Что такое DaemonSet и зачем он здесь?

**Что сказать:**

> DaemonSet запускает по одному Pod на каждом подходящем сервере. У меня так запускается Vector, потому что он должен собирать логи приложений с каждого сервера.

**Что будет, если удалить:**

- Если удалить только Pod Vector, DaemonSet заметит это и создаст новый.
- Если удалить сам DaemonSet, Vector больше не будет автоматически запускаться.
- Приложение, скорее всего, продолжит работать, но новые логи перестанут уходить в VictoriaLogs.

**Почему не Deployment:** Deployment может запустить несколько Pod где угодно. Он не гарантирует, что сборщик логов будет на каждом сервере.

### 2. Мы увеличили число Pod приложения. Как уменьшить нагрузку на БД?

**Что сказать:**

> Дополнительные Pod не уменьшают нагрузку на БД. Наоборот, они могут открыть больше соединений и отправить больше запросов. Сначала нужно найти причину нагрузки, а затем оптимизировать запросы, ограничить число соединений, добавить кэш или использовать отдельную копию БД для чтения.

Простые варианты:

- исправить медленные запросы;
- добавить нужные индексы;
- ограничить количество соединений каждого Pod с БД;
- кэшировать часто запрашиваемые данные;
- чтения отправлять в read replica — копию БД для чтения;
- тяжёлую работу выполнять через очередь постепенно.

**Пример:** было 3 Pod по 10 соединений — максимум 30 соединений. Стало 10 Pod — уже до 100 соединений. База может не выдержать.

### 3. Мы изменили Secret. Обновятся ли Pod?

**Что сказать:**

> Обычно нет. Изменение Secret само по себе не перезапускает Deployment или StatefulSet. Если секрет передан через переменную окружения, старые Pod продолжат использовать старое значение. Поэтому я запускаю контролируемый rollout.

Команда для Deployment:

```bash
kubectl rollout restart deployment/api
```

Если Secret подключён как файл, Kubernetes может обновить файл без перезапуска. Но приложение ещё должно уметь перечитать этот файл. Поэтому на защите безопасно сказать: «Способ обновления зависит от того, как Secret подключён, а для предсказуемости я делаю rollout».

### 4. Зачем нужен PVC?

**Что сказать:**

> PVC нужен, чтобы получить постоянный диск. Обычные файлы внутри Pod могут исчезнуть вместе с Pod, а данные на постоянном диске можно подключить к новому Pod.

Примеры данных для PVC:

- данные базы;
- очередь на диске;
- накопленные логи Vector, которые ещё не отправлены.

Важно:

- удаление Pod обычно не удаляет PVC;
- удаление PVC уже может привести к потере данных;
- PVC не является резервной копией;
- для временных данных постоянный диск может быть не нужен.

### 5. Что такое решардинг?

**Что сказать:**

> Шардинг — это разделение данных между несколькими серверами. Решардинг — изменение этого разделения: например, мы добавили новый сервер и переносим на него часть данных.

Безопасный порядок:

1. Создать новое размещение данных.
2. Скопировать туда старые данные.
3. Не забывать переносить новые изменения, которые приходят во время копирования.
4. Проверить, что данные совпадают.
5. Переключить чтение на новое место.
6. Только потом удалить старую копию.

**Главный риск:** часть данных записалась в старое место, а часть — в новое. Поэтому нужны проверки и возможность повторить перенос.

### 6. Что сделает Vector, если VictoriaLogs недоступна?

**Что сказать:**

> Vector попробует отправить логи повторно. Пока VictoriaLogs недоступна, логи будут накапливаться в буфере. Если буфер закончится, Vector либо замедлит чтение новых логов, либо начнёт их терять — это зависит от настроек.

Варианты буфера:

- **В памяти:** работает быстро, но накопленные логи пропадут при перезапуске Vector.
- **На диске:** медленнее, зато лучше переживает перезапуск.

Что будет при долгом сбое:

- буфер заполнится;
- файлы с логами на сервере продолжат расти;
- может закончиться место на диске;
- часть логов может потеряться;
- после восстановления Vector начнёт отправлять накопившиеся логи и может снова перегрузить VictoriaLogs.

Что контролировать:

- ошибки отправки;
- размер буфера;
- свободное место на диске;
- количество потерянных логов.

## Похожие вопросы с короткими ответами

### Почему Pod после удаления появился снова?

Потому что Deployment, StatefulSet или DaemonSet следит за нужным количеством Pod и создаёт недостающий.

### Почему Pod находится в состоянии Pending?

Kubernetes пока не смог выбрать для него сервер или подключить диск. Частые причины: не хватает CPU/памяти, не подходит ни один сервер или не готов PVC.

### Pod имеет статус Running. Значит ли это, что он получает запросы?

Нет. `Running` означает, что контейнер запущен. Для получения трафика Pod ещё должен пройти readiness probe и попасть в Service.

### Зачем нужны requests и limits?

`requests` показывают, сколько ресурсов нужно Pod для размещения. `limits` ограничивают максимальное потребление. При слишком маленьком лимите памяти приложение могут завершить, а при маленьком лимите CPU оно будет работать медленнее.

### Чем readiness отличается от liveness?

Readiness решает, отправлять ли в Pod новые запросы. Liveness решает, нужно ли перезапустить зависший контейнер.

### Почему liveness не стоит проверять через БД?

Если БД упадёт, все Pod могут одновременно начать перезапускаться. Это не починит БД и только ухудшит ситуацию.

### Зачем нужен Service?

Pod могут пересоздаваться и менять IP. Service даёт постоянный адрес и направляет запросы в готовые Pod.

### Pod отвечает напрямую, но Service не работает. Почему?

Возможно, Service выбирает не те Pod, Pod не прошёл readiness или в Service указан неправильный порт.

### Зачем несколько replicas?

Чтобы обрабатывать больше запросов и продолжать работу при потере одного Pod. Но если все Pod находятся на одном сервере или используют одну сломанную БД, полной отказоустойчивости всё равно нет.

### Спасёт ли HPA медленную БД?

Не обязательно. HPA добавит Pod, а они могут создать ещё больше запросов и соединений с БД.

### Что произойдёт при удалении Pod с PVC?

Обычно новый Pod подключит тот же постоянный диск и увидит данные. Но точное поведение зависит от настроек хранилища.

### Можно ли просто увеличить StatefulSet базы с одного Pod до трёх?

Kubernetes создаст ещё два Pod, но сам не скопирует между ними данные. Репликацию должна настраивать сама БД или специальный operator.

### Что такое graceful shutdown?

Корректное завершение: приложение перестаёт принимать новые запросы, заканчивает уже начатые и только потом выключается.

### Что такое rollback?

Возврат приложения к предыдущей версии. Он не возвращает старое состояние базы данных автоматически.

### Почему после восстановления VictoriaLogs снова может упасть?

Все Vector-агенты одновременно начнут отправлять накопившиеся логи. Получится резкий скачок нагрузки.

## Как отвечать, если не уверен

Не нужно угадывать. Можно сказать:

> Это зависит от настроек. Я бы сначала посмотрел, как объект подключён и кто им управляет. Затем проверил бы события Kubernetes, логи и метрики.

Полезная схема любого ответа:

1. Что делает компонент?
2. Кто его автоматически восстанавливает?
3. Что перестанет работать при отказе?
4. Потеряются ли данные?
5. Как я это замечу?
