# Go VCV: вопросы и эталонные ответы

Шпаргалка для асинхронного видеоинтервью на стажировку Go. Основной ответ на каждый вопрос рассчитан примерно на 40–60 секунд. Блоки «Если спросят глубже» нужны для подготовки к уточнениям и техническому интервью.

Эталонный ответ — не текст для дословного заучивания. Лучше сохранить структуру ответа и пересказать её своими словами.

## Как строить ответ

Для теоретического вопроса:

1. дать определение одним предложением;
2. объяснить основной принцип работы;
3. привести короткий пример применения;
4. назвать одну важную особенность или ловушку.

Для вопроса о личном опыте:

1. кратко описать ситуацию;
2. назвать свою задачу;
3. объяснить свои действия;
4. закончить результатом и выводом.

## 1. Основы Go

### 1. Что такое zero value?

**Ответ:** Zero value — это значение, которое переменная получает автоматически, если её объявили без явной инициализации. Для чисел это `0`, для `bool` — `false`, для строки — `""`, а для указателей, слайсов, map, каналов, функций и интерфейсов — `nil`. Поля структуры тоже получают zero value своих типов. Поэтому в Go не бывает переменных с неопределённым значением.

### 2. Чем массив отличается от слайса?

**Ответ:** Массив — это значение фиксированной длины, причём длина является частью типа: `[3]int` и `[4]int` — разные типы. Слайс — это динамическое представление последовательности элементов поверх базового массива. Он содержит ссылку на данные, длину и ёмкость. Слайсы обычно используют в прикладном коде, потому что их размер можно увеличивать через `append`.

**Важно:** несколько слайсов могут ссылаться на один базовый массив, поэтому изменение через один слайс иногда видно через другой.

### 3. Что означают `len` и `cap` у слайса?

**Ответ:** `len` — число элементов, к которым сейчас можно обращаться, а `cap` — сколько элементов помещается от начала слайса до конца его базового массива без выделения нового массива. Если при `append` ёмкости не хватает, runtime выделяет новый массив и переносит туда элементы. Поэтому после `append` слайс может перестать разделять данные с исходным слайсом.

### 4. Чем nil-слайс отличается от пустого слайса?

**Ответ:** У обоих длина равна нулю, их можно перебирать и передавать в `append`. Но nil-слайс равен `nil`, а явно созданный пустой слайс `[]int{}` — нет. На практике они почти взаимозаменяемы, но могут по-разному сериализоваться: например, в JSON это часто `null` и `[]`.

### 5. Что такое `map` и как проверить наличие ключа?

**Ответ:** `map` — это встроенная хеш-таблица, которая хранит пары ключ—значение. Чтение отсутствующего ключа возвращает zero value типа значения, поэтому для проверки существования используют форму `value, ok := m[key]`. Если `ok` равен `false`, ключа нет. Порядок обхода map не гарантирован.

### 6. Можно ли работать с nil-map?

**Ответ:** Из nil-map можно безопасно читать: будет возвращено zero value и `ok == false`. Но запись в nil-map вызывает panic. Для записи map нужно инициализировать через `make` или литерал. Встроенная map также не поддерживает безопасную конкурентную запись без дополнительной синхронизации.

### 7. Чем `make` отличается от `new`?

**Ответ:** `new(T)` выделяет память под значение типа `T`, заполняет его zero value и возвращает указатель `*T`. `make` применяется только к слайсам, map и каналам: оно инициализирует их внутреннюю структуру и возвращает готовое значение самого типа, а не указатель на него. На практике `new` используется редко, а `make` нужен, например, перед записью в map или работой с каналом.

### 8. Для чего нужны указатели?

**Ответ:** Указатель хранит адрес значения. Он позволяет функции или методу изменять исходный объект и помогает не копировать крупные структуры. В Go нет арифметики указателей в обычном безопасном коде. Перед разыменованием нужно учитывать, что указатель может быть `nil`, иначе программа получит panic.

### 9. Что такое структура и метод?

**Ответ:** Структура объединяет именованные поля разных типов в одно значение. Метод — это функция с receiver, связанная с определённым типом. Value receiver получает копию значения, а pointer receiver позволяет изменять исходный объект и избегать копирования структуры. Обычно методы одного типа стараются последовательно объявлять либо на значении, либо на указателе.

### 10. Что такое интерфейс в Go?

**Ответ:** Интерфейс задаёт набор методов, то есть требуемое поведение. Тип реализует интерфейс неявно, если имеет все необходимые методы — специальное объявление `implements` не нужно. Это уменьшает связанность: функция может принимать не конкретную структуру, а минимальное необходимое поведение. Хорошая практика — объявлять небольшие интерфейсы рядом с кодом, который их использует.

### 11. Почему интерфейс с nil-указателем может быть не равен `nil`?

**Ответ:** Значение интерфейса концептуально содержит динамический тип и динамическое значение. Интерфейс равен `nil`, только если обе части отсутствуют. Если положить в интерфейс nil-указатель типа `*MyError`, динамический тип сохранится, поэтому сам интерфейс уже не равен `nil`. Это частая причина функций, которые неожиданно возвращают ненулевой `error`.

### 12. Что такое `defer`?

**Ответ:** `defer` откладывает вызов функции до выхода из текущей функции. Отложенные вызовы выполняются в обратном порядке, даже если выход происходит из-за panic. `defer` удобно использовать для `Unlock`, `Close` и другой очистки ресурсов рядом с их получением. При этом аргументы отложенного вызова вычисляются в момент выполнения строки `defer`.

## 2. Ошибки и context

### 13. Как в Go обрабатываются ошибки?

**Ответ:** Ошибка в Go обычно возвращается как последнее значение функции. Вызывающий код проверяет `err != nil` и решает, что делать: обработать ошибку, добавить контекст или вернуть выше. Встроенный `error` — это интерфейс с методом `Error() string`. Такой явный подход делает ошибочные ветви видимыми в обычном потоке управления.

### 14. Как добавить контекст к ошибке?

**Ответ:** Ошибку обычно оборачивают через `fmt.Errorf` с `%w`, например `fmt.Errorf("read config: %w", err)`. Так сообщение объясняет, на каком уровне произошёл сбой, а исходная ошибка остаётся доступной через `errors.Is` и `errors.As`. Не стоит добавлять один и тот же бессодержательный текст на каждом уровне.

### 15. Чем отличаются `errors.Is` и `errors.As`?

**Ответ:** `errors.Is` проверяет, есть ли в цепочке конкретная ошибка, например `errors.Is(err, fs.ErrNotExist)`. `errors.As` ищет ошибку определённого типа и, если находит, записывает её в переданную переменную. `Is` нужен для сравнения по смыслу, а `As` — когда нужны дополнительные поля или методы конкретного типа ошибки.

### 16. Когда использовать `panic`, а когда `error`?

**Ответ:** Ожидаемые проблемы — неправильный ввод, отсутствие файла, сетевой сбой — возвращают как `error`. `panic` используют, когда нарушен внутренний инвариант и нормальное продолжение невозможно. Во время panic выполняются `defer`, после чего программа завершится, если panic не перехвачен через `recover`. `panic` не следует использовать как обычный способ обработки ошибок.

### 17. Для чего нужен `context.Context`?

**Ответ:** Контекст передаёт по цепочке вызовов сигнал отмены, deadline и небольшие request-scoped значения. Например, если клиент отменил HTTP-запрос, связанные обращения к базе и внешним сервисам тоже должны завершиться. Контекст обычно передают первым параметром и не хранят в структуре. Функция, создавшая контекст через `WithCancel` или `WithTimeout`, должна вызвать `cancel`, чтобы освободить ресурсы.

## 3. Горутины и конкурентность

### 18. Что такое конкурентность и чем она отличается от параллелизма?

**Короткий ответ:** Конкурентность — это организация программы так, чтобы несколько задач могли независимо продвигаться и ожидать друг друга. Параллелизм — физическое одновременное выполнение задач на нескольких ядрах. Конкурентная программа может работать даже на одном ядре за счёт переключения между задачами, а параллельность требует возможности выполнять их одновременно.

**Если спросят глубже:** Конкурентность — свойство структуры программы, параллелизм — свойство конкретного исполнения. Горутины дают удобную модель конкурентности, а runtime Go может выполнять их параллельно в зависимости от доступных процессоров и `GOMAXPROCS`.

### 19. Что такое горутина?

**Короткий ответ:** Горутина — лёгкая конкурентная функция, которой управляет runtime Go. Её запускают оператором `go`. Горутины дешевле системных потоков, имеют растущий стек, а runtime распределяет множество горутин по потокам ОС. Но горутина не бесплатна: нужно понимать, когда она завершится, кто получит её результат и как передать ей отмену.

### 20. Чем горутина отличается от потока ОС?

**Короткий ответ:** Потоком управляет операционная система, и его создание и переключение обычно дороже. Горутина управляется runtime Go, начинается с небольшого стека, который может расти, и множество горутин выполняются поверх меньшего числа потоков ОС. Это позволяет удобно запускать много конкурентных операций, особенно связанных с ожиданием I/O.

**Если спросят про планировщик:**

- **G** — goroutine, то есть выполняемая задача;
- **M** — machine, системный поток;
- **P** — processor, ресурс runtime, необходимый M для исполнения Go-кода.

Планировщик распределяет готовые G по P и M. При блокирующем системном вызове runtime старается дать P другому M, чтобы остальные горутины продолжили работу. Это упрощённая модель; для стажёрского ответа обычно достаточно идеи мультиплексирования горутин на потоки.

### 21. Как дождаться завершения нескольких горутин?

**Ответ:** Для ожидания группы горутин используют `sync.WaitGroup`. До запуска горутины увеличивают счётчик через `Add`, каждая горутина вызывает `Done`, а ожидающий код вызывает `Wait`. `Add` важно делать до `go`, иначе `Wait` может увидеть нулевой счётчик и завершиться слишком рано. Для задач с ошибками и общей отменой часто удобнее группа, связанная с контекстом.

### 22. Что такое data race?

**Короткий ответ:** Data race возникает, когда несколько горутин одновременно обращаются к одной области памяти, хотя бы одна операция является записью и между операциями нет синхронизации. Это делает поведение программы ненадёжным. Гонку устраняют через mutex, каналы, atomics или отказ от совместно изменяемого состояния. Для обнаружения используют `go test -race ./...`.

**Важно:** race detector находит только гонки, которые проявились во время конкретного запуска тестов.

### 23. Чем data race отличается от race condition?

**Ответ:** Data race — конкретная несинхронизированная работа с общей памятью. Race condition — более широкая логическая зависимость результата от порядка событий. Например, операция «проверить баланс, затем списать» может быть логически некорректна даже тогда, когда отдельные чтения и записи защищены mutex. Поэтому отсутствие предупреждений race detector ещё не доказывает корректность конкурентного алгоритма.

### 24. Для чего нужен `sync.Mutex`?

**Ответ:** Mutex обеспечивает взаимное исключение: одновременно критическую секцию выполняет только одна горутина. Его используют, когда несколько горутин работают с общим изменяемым состоянием и нужно сохранить инвариант сразу нескольких операций или полей. Все обращения к защищаемым данным должны соблюдать один протокол блокировки. Mutex нельзя копировать после начала использования.

### 25. Когда использовать mutex, а когда канал?

**Ответ:** Mutex удобен для защиты уже существующего общего состояния, например map или нескольких связанных полей. Канал удобен для передачи данных, распределения работы и сигналов между горутинами. Выбор зависит не от правила «каналы всегда лучше», а от модели владения: если данные принадлежат одному worker и остальные отправляют ему команды, подходит канал; если нескольким методам нужен короткий защищённый доступ к структуре, mutex обычно проще.

### 26. Что такое deadlock?

**Ответ:** Deadlock — ситуация, когда участники навсегда ждут друг друга и никто не может продолжить выполнение. В Go это может быть отправка в канал без получателя, чтение из канала, который никто не закроет и не заполнит, или захват mutex в несовместимом порядке. Буфер канала иногда откладывает блокировку, но не исправляет ошибку протокола.

### 27. Что такое goroutine leak?

**Короткий ответ:** Утечка горутины возникает, когда горутина больше не нужна, но не может завершиться, например навсегда ждёт канал или сетевую операцию без deadline. Такая горутина продолжает занимать память и удерживать ссылки на другие объекты. Поэтому для каждой запущенной горутины нужно понимать условие завершения и предусматривать отмену через закрытие канала или `context`.

**Типичные причины:**

- отправка без получателя;
- чтение из канала, который никто не закроет;
- downstream перестал читать pipeline, а upstream продолжает отправлять;
- сетевой вызов не имеет timeout;
- ticker не остановлен;
- worker не слушает сигнал отмены.

### 28. Что такое worker pool?

**Ответ:** Worker pool — это ограниченное число горутин, которые читают задачи из общего канала. Он нужен, чтобы контролировать уровень конкурентности и не создавать по горутине на неограниченное число задач. Владелец отправляет задания и закрывает канал заданий, workers завершаются после его опустошения, а отдельная координирующая горутина может закрыть канал результатов после `WaitGroup`.

## 4. Каналы

### 29. Что такое канал?

**Короткий ответ:** Канал — типизированный механизм передачи значений и синхронизации между горутинами. Его создают через `make(chan T)`. Отправка и получение могут блокироваться, поэтому канал одновременно передаёт данные и задаёт порядок событий. Каналы особенно удобны для очередей заданий, pipeline и передачи результата фоновой работы.

### 30. Чем буферизованный канал отличается от небуферизованного?

**Короткий ответ:** В небуферизованном канале отправка завершается только тогда, когда другая горутина готова принять значение — это точка синхронизации. В буферизованном канале отправка завершается, пока в буфере есть место, а получение — пока в нём есть данные. Размер буфера определяет допустимое число элементов в очереди, но буфер не является универсальным способом исправить deadlock.

**Таблица блокировок:**

| Операция | Когда продолжает работу | Когда блокируется |
|---|---|---|
| Send в unbuffered | готов receiver | receiver отсутствует |
| Receive из unbuffered | готов sender | sender отсутствует |
| Send в buffered | есть свободное место | буфер заполнен |
| Receive из buffered | есть значение | буфер пуст и канал открыт |

### 31. Зачем закрывать канал и кто должен это делать?

**Короткий ответ:** Закрытие сообщает получателям, что новых значений больше не будет. Обычно канал закрывает отправитель или координатор, который точно знает, что все отправки завершены. Получатель не обязан закрывать канал: канал закрывают не для освобождения памяти, а для передачи факта завершения потока данных.

**Важно:** если отправителей несколько, они не должны независимо пытаться закрыть общий канал. Закрытие координирует один владелец, например после ожидания всех producers через `WaitGroup`.

### 32. Что произойдёт при работе с закрытым каналом?

**Ответ:** Получатель сначала прочитает оставшиеся значения из буфера. После опустошения каждое чтение немедленно возвращает zero value и `ok == false`. Цикл `for value := range ch` автоматически завершится. Отправка в закрытый канал вызывает panic, как и повторный `close`.

### 33. Чем nil-канал отличается от закрытого?

**Ответ:** Операции отправки и получения с nil-каналом блокируются навсегда, а `close(nilChannel)` вызывает panic. Из закрытого канала, наоборот, можно читать без блокировки: после данных будут приходить zero value и `ok == false`. Этим свойством nil-канала иногда пользуются, чтобы временно выключить ветку `select`.

### 34. Для чего нужен `select`?

**Короткий ответ:** `select` ждёт готовности одной из нескольких операций с каналами. Если готовы несколько веток, выбирается одна из них псевдослучайно. Его используют, например, чтобы одновременно ждать данные и отмену контекста. Ветка `default` делает `select` неблокирующим, но цикл с `default` без паузы может постоянно занимать CPU.

```go
select {
case job := <-jobs:
	process(job)
case <-ctx.Done():
	return ctx.Err()
}
```

### 35. Может ли канал заменить очередь?

**Ответ:** Буферизованный канал может выполнять роль ограниченной очереди внутри процесса: он хранит значения и создаёт backpressure, когда заполнен. Но это не полноценный брокер сообщений: данные не переживают перезапуск процесса, нет долговременного хранения и подтверждений доставки. Размер буфера должен быть обоснован допустимой нагрузкой и задержкой, а не выбран случайно.

### 36. Как корректно остановить producer, если consumer больше не читает?

**Ответ:** Отправка не должна бесконечно ждать канал. Её оборачивают в `select`, где вторая ветка слушает `ctx.Done()` или отдельный канал отмены. Тогда consumer или владелец pipeline может отменить работу, и upstream-горутины завершатся. Просто прекратить чтение без сигнала upstream — типичная причина утечки горутин.

```go
select {
case out <- value:
case <-ctx.Done():
	return
}
```

## 5. Сборщик мусора и память

### 37. Что делает сборщик мусора в Go?

**Короткий ответ:** Сборщик мусора автоматически освобождает память объектов в heap, которые больше недостижимы из работающей программы. Разработчику не нужно вручную вызывать освобождение памяти, но он всё равно должен закрывать внешние ресурсы — файлы, соединения и response body. GC занимается памятью, а не произвольными ресурсами операционной системы.

### 38. Как в общих чертах работает GC в Go?

**Ответ для VCV:** В Go используется конкурентный трассирующий сборщик. Он начинает с корней — например, глобальных переменных и стеков горутин — и отмечает достижимые объекты. Неотмеченные объекты считаются мусором, и их память можно использовать повторно. Основная часть маркировки выполняется конкурентно с программой, но небольшие stop-the-world фазы всё равно нужны для начала и завершения цикла.

**Если спросят глубже:** Упрощённо маркировку описывают трёхцветной моделью:

- белые объекты ещё не исследованы;
- серые найдены, но их ссылки ещё нужно просмотреть;
- чёрные исследованы полностью.

Write barrier помогает сохранять корректность графа объектов, пока приложение параллельно меняет ссылки. После маркировки недостижимая память освобождается на этапе sweep. Runtime также может возвращать неиспользуемые страницы операционной системе через scavenger.

### 39. Что такое stop-the-world?

**Ответ:** Stop-the-world — короткая фаза, во время которой выполнение пользовательского Go-кода временно приостанавливается, чтобы runtime безопасно выполнить часть работы GC. Современный GC Go делает основную маркировку конкурентно, поэтому паузы не охватывают весь цикл сборки. Однако GC всё равно потребляет CPU и может влиять на задержки приложения.

### 40. Чем stack отличается от heap?

**Короткий ответ:** Стек связан с выполнением конкретной горутины и обычно используется для локальных данных с понятным временем жизни. Heap хранит объекты, которые должны жить дольше вызова функции или доступны из нескольких мест. Размещение выбирает компилятор с помощью escape analysis, а не программист напрямую. Возврат указателя на локальную переменную в Go безопасен: при необходимости значение будет размещено в heap.

### 41. Что такое escape analysis?

**Ответ:** Escape analysis — анализ компилятора, определяющий, может ли значение безопасно находиться на стеке или должно быть размещено в heap. Например, если ссылка на локальную переменную переживает вызов функции, значение обычно «убегает» в heap. Heap allocation не является ошибкой, но большое число аллокаций увеличивает работу GC. Решения компилятора можно исследовать через диагностические флаги сборки.

### 42. Освобождает ли GC файлы и сетевые соединения?

**Ответ:** Рассчитывать на это нельзя. GC управляет памятью Go, но внешние ресурсы имеют собственный жизненный цикл. Файл нужно закрывать через `Close`, тело HTTP-ответа — через `resp.Body.Close`, ticker — через `Stop`. Обычно освобождение оформляют через `defer` сразу после успешного получения ресурса.

### 43. Может ли в Go быть утечка памяти при наличии GC?

**Ответ:** Да. GC освобождает только недостижимые объекты. Если программа продолжает хранить ссылку на уже ненужные данные — например, в глобальной map, кэше без удаления, длинноживущем слайсе или зависшей горутине — объект остаётся достижимым и не удаляется. Поэтому логические утечки памяти возможны и в языке со сборщиком мусора.

### 44. Как слайс может удерживать большой объём памяти?

**Ответ:** Маленький слайс может ссылаться на небольшой участок большого базового массива и тем самым удерживать весь массив в памяти. Например, если сохранить короткий фрагмент большого буфера, GC не сможет освободить массив, пока существует этот слайс. Если данные должны жить долго, нужную часть иногда копируют в отдельный слайс.

### 45. Что такое `GOGC`?

**Ответ:** `GOGC` управляет компромиссом между расходом памяти и частотой сборок. Значение по умолчанию обычно означает, что следующий цикл GC запускается после заметного роста живого heap относительно объёма, оставшегося после предыдущей сборки. Большее значение уменьшает частоту GC, но увеличивает память; меньшее — экономит память ценой дополнительной работы CPU. Обычно параметр меняют только после измерений.

### 46. Как уменьшить нагрузку на GC?

**Ответ:** Сначала нужно измерить аллокации и профиль памяти, а затем уменьшать ненужные выделения: переиспользовать подходящие буферы, заранее задавать ёмкость слайсов, избегать лишних преобразований и не удерживать ссылки на большие объекты. Нельзя оптимизировать вслепую: пул объектов или ручное переиспользование могут усложнить код и даже ухудшить результат.

## 6. Тестирование и инструменты

### 47. Как устроены тесты в Go?

**Ответ:** Тесты обычно находятся в файлах с суффиксом `_test.go`, а тестовые функции имеют вид `func TestName(t *testing.T)`. Их запускают командой `go test ./...`. Часто используют table-driven подход: набор входов и ожидаемых результатов описывают таблицей и запускают одинаковую проверку для каждого случая.

### 48. Для чего нужен race detector?

**Ответ:** Race detector инструментирует программу и во время выполнения ищет несинхронизированный конкурентный доступ к памяти. Для тестов его запускают через `go test -race ./...`. Он полезен, но не является доказательством отсутствия гонок: инструмент проверяет только реально выполненные пути, поэтому нужны хорошие конкурентные тесты.

### 49. Какие инструменты качества Go ты знаешь?

**Ответ:** `gofmt` автоматически форматирует код, `go test` запускает тесты, `go vet` ищет подозрительные конструкции, а `go test -race` — гонки данных. Для производительности есть benchmarks и `pprof`, для зависимостей — Go modules. На собеседовании лучше не просто перечислить инструменты, а привести пример, какую проблему каждый из них решает.
